## 1. 为什么要做阶段6

阶段 0-5 已经把平台能力基本做完了，但"能做"和"好用、好接手、好维护"还不是一回事。当前真正缺的不是底层能力，而是把现有能力整理成一套**可持续使用、可持续交接、可持续扩展**的体系。

结合当前仓库现状，主要问题不是单点缺失，而是以下几类问题叠在一起：

1. **文档入口不统一**
   - README（当前 512 行）、使用手册（153 行）、树莓派控制程序开发手册（当前 458 行）、实体 README、阶段文档各自有内容，但面向不同读者的边界不够清楚。
   - 新用户不知道先看什么，老用户也不容易快速找到最新口径。

2. **"会用平台"与"会扩展平台"之间有断层**
   - 已经有控制程序开发说明、benchmark 工具、阶段5研究工具，但"从零写一个自己的算法并接入完整研究流程"的路径仍然分散。
   - "树莓派实例怎么写""如何接入 benchmark""如何做对比、诊断、出图"需要一条完整链路，而不是散落说明。

3. **实例体系不完整**
   - 当前平台已经支持 3D 目标、双轴云台、观测模式、延时链路、ATP 状态机、研究工具链，但缺少一组面向使用者的"标准实例/标准场景/标准操作流程"。
   - 用户提到的二维平面、三维空间、多种典型运动模式，目前更接近"能力存在"，还没有整理成"拿来就能跑"的实例体系。

4. **界面与入口文档没有完全对齐最新能力**
   - 当前 GUI（`simulation/gui/window.py`）已支持以下字段：
     - **核心面板**：仿真时间、控制模式、yaw/pitch、角速度、角度误差、u/v、偏差 du/dv、在视野内、backlog、obs_lag
     - **诊断面板**：各实体完整状态（含目标 x/y/z/vx/vy/vz 三维坐标和速度）
     - **世界视图**：目标轨迹、云台指向、FOV 弧
     - **时间线**：像素误差、角度误差、角速度
   - **仍然缺失的表达**（基于代码盘点确认）：
     - ATP 状态（SEARCH/ACQUIRE/TRACK_COARSE/TRACK_FINE/LOST/REACQUIRE）未在 GUI 任何位置显示
     - obs_mode（debug/research/realistic）在 `build_runtime()` 中传入但从未在界面展示
     - 当前 target_type（运动类型名称）和 waypoints 配置未展示
     - 3D 目标只有原始坐标数值，缺少运动模式语义表达
   - 因此阶段6应避免误判为"推翻重做 GUI"，而应聚焦**基于现状做准确定义和增量适配**。

5. **部分工具、示例和旧口径存在混杂风险**
   - `tools/` 下现有 16 个脚本，其中 14 个主流程/辅助工具、1 个内部辅助工具（`_analyze_tracking.py`，下划线前缀）、1 个历史演示脚本（`run_raspi_tracking_demo.py`）。
   - 哪些是主流程工具、哪些是辅助工具、哪些是历史工具、哪些仍需保留，都需要统一标注和治理。

6. **缺少维护治理规则**
   - 未来继续新增算法、场景、文档或工具时，缺少一套明确的更新规则：
     - 改完代码后要同步哪些文档
     - 新增实例放哪里
     - 旧工具怎么标记
     - README 只保留什么
   - 如果不先收口，后面内容会继续变散。

## 2. 阶段6的核心定位

阶段6不是再做一轮底层能力开发，而是把阶段0-5已经形成的平台，整理成一套：

1. **能快速上手的系统手册**
2. **能直接拿来运行的实例体系**
3. **能稳定扩展的接入指南**
4. **能长期维护的治理规则**
5. **与当前系统状态一致的主界面与入口口径**

因此，阶段6本质上是：

**"平台交付形态整理 + 文档体系重构 + 实例体系补全 + GUI/入口适配 + 维护规则建立"**

这份盘点不是附属材料，而是阶段6后续需求拆分、优先级排序和验收的依据。

## 4. 目标受众

阶段6服务的对象至少包括以下四类：

1. **日常研究使用者**
   - 希望快速知道怎么运行、怎么对比、怎么诊断、怎么出图。

2. **新接手人员**
   - 希望从零理解平台结构、实例、工具和扩展方式。

3. **算法开发者**
   - 希望把自己的控制程序、跟踪器、预测器、对比方案接入平台。

4. **项目维护者**
   - 希望后续继续迭代时，不会把文档、示例、工具和界面再做散。

### 5.3 需求三：实例体系与典型场景模板补全

当前问题：
- 当前平台已支持 5 种目标运动类型（sinusoidal、constant_velocity、constant_accel、random_walk、waypoint），3D 空间运动，双轴云台，3 种观测模式（debug/research/realistic），延时链路，ATP 状态机，6 个算法基线，但缺少一套明确的"标准实例体系"。
- 用户明确提出希望有二维平面实例、三维空间实例，以及几种典型运动模式。
- 现在更多是"知道参数可以这么配"，不是"拿一个现成模板直接用"。

需要：
- 为当前平台定义一套标准实例分类，至少包括：
  - 快速验证实例（冒烟测试级别，30 秒内完成）
  - 2D 平面研究实例
  - 3D 空间研究实例
  - 延时退化实例（不同 delay-ms 对比）
  - 研究对比实例（benchmark 全流程）
- 为 2D 和 3D 各整理若干典型场景模板，覆盖 5 种运动类型：
  - 2D 模板：匀速直线（constant_velocity）、正弦横移（sinusoidal）、随机游走（random_walk）、平面航点巡航（waypoint）
  - 3D 模板：匀速穿越、含垂直起伏的振荡、三维航点巡航、接近/远离类运动
- 每个模板都要明确：
  - 场景目的
  - 适用算法类型
  - 关键参数
  - 直接可运行命令
  - 预期现象
  - 对应输出去哪里看
- 实例不仅是命令清单，还要说明"实例之间如何配合使用"。

说明：
- 这里的重点不是立即扩底层运动模型，而是先把现有能力整理成可复用实例。
- 如果盘点后确认现有 5 种运动模式不足以覆盖典型研究场景，再作为后续增补需求单列。

### 5.4 需求四：树莓派控制程序编写与新算法接入指南收口

当前问题：
- 当前已有 `docs/树莓派控制程序开发手册.md`（当前 458 行），是目前最完整的专项手册，覆盖了控制程序协议、obs 结构、两种开发模式（直接式/可插拔 ATP）、测试方法论。
- 但它和 benchmark（`run_benchmark.py` + `ALGORITHM_REGISTRY`）、阶段5研究工具（compare/diagnose/plot）之间还没有完全打通成一条统一链路。
- 缺少"从写控制程序到完成一轮研究对比"的完整端到端流程说明。
- 缺少"临时加载 vs 正式注册到 benchmark"两种接入方式的明确区分。

需要：
- 基于现有 458 行手册补成一条完整接入路径：
  - 写控制程序（最小示例 → 完整示例）
  - 本地运行调试（`--control-program module:Class`）
  - 接入主运行入口
  - 接入 benchmark（临时运行 vs 注册到 `ALGORITHM_REGISTRY`）
  - 做回归对比（`compare_results.py`）
  - 做诊断分析（`diagnose_algorithm.py`）
  - 做出图与结果归档（`plot_comparison.py`）
- 明确区分几种"接入方式"：
  - 只想临时加载自己的控制程序（`--control-program` 参数）
  - 想把算法长期纳入 benchmark 注册表（修改 `tools/run_benchmark.py` 的 `ALGORITHM_REGISTRY`）
  - 想新增 tracker / predictor / ATP 组合（涉及 tracker_program.py 扩展）
- 给出最小示例、完整示例、常见错误和建议目录组织方式。
- 如内容过长，可拆出 `docs/algorithm_integration_guide.md` 独立文档。

  - 典型命令
  - 与其他工具的衔接关系

说明：

### 5.6 需求六：主运行界面与入口口径适配

当前问题：
- 不能简单把现状描述为"仍是一轴系统"，因为当前 GUI 已经显示 yaw/pitch、u/v、backlog/obs_lag 等双轴与链路信息。
- 真实问题（基于 `simulation/gui/window.py` 代码盘点确认）在于：
  - **ATP 状态**：GUI 任何位置均未显示 ATP 状态机当前状态（SEARCH/ACQUIRE/TRACK_COARSE/TRACK_FINE/LOST/REACQUIRE）
  - **观测模式**：obs_mode 在 `build_runtime()` 中传入（CLI 参数 `--obs-mode`），但 GUI 未展示
  - **场景信息**：target_type（运动类型名称）和 waypoints 配置未在 GUI 展示
  - **3D 语义**：目标只有原始 x/y/z/vx/vy/vz 数值，缺少运动模式名称等语义表达
  - 入口层（README/手册/app.py/CLI/GUI）对"主运行方式"的叙述不够统一

需要：
- 先做界面盘点，再定义 GUI 增量更新范围。
- GUI 更新目标应聚焦于"表达当前系统真实状态"，而不是重写框架。
- 至少应考虑：
  - ATP 状态显示（可加在核心面板或诊断面板）
  - 当前 obs_mode 显示（可加在工具栏或核心面板）
  - 当前场景/实例信息显示（可加在窗口标题或核心面板）
  - 与 3D 目标、光源目标语义一致的展示口径
  - 主入口文档与 GUI 行为一致

修改范围（基于代码结构确认）：
- `simulation/gui/window.py`：核心面板 `_update_core_tab()`（约 L630-664）、诊断面板 `_update_diag_tab()`（约 L666-711）
- `simulation/cli.py`：帮助文案和参数说明（L13-42）
- 必要时同步 README / 主手册截图与说明

特别说明：
- `app.py` 当前仅 7 行（纯透传到 `simulation.cli.main()`），通常不需要单独修改。
- 但 ATP 状态显示不能仅按“改 `window.py` 数行标签”来估计，因为当前快照里的 `snapshot.raspi` 尚未暴露 ATP 状态；若纳入本轮 GUI 适配，需先补齐状态暴露链路。
- 因此阶段6不应把"修改 app.py"本身作为主要目标，而应把"统一主入口使用口径"作为目标。

## 6. 不做什么

阶段6默认不包括以下内容，除非盘点后另行确认：

1. 不新增新的底层物理实体

4. 不推翻重写 GUI
5. 不凭主观判断删除历史工具

## 9. 阶段6验收口径

阶段6完成时，至少应满足以下结果：

1. 新用户能通过 README 快速找到正确入口，不会在阶段文档和主手册之间迷路。
2. 使用者能按照一条清晰路径完成：运行实例 → 跑 benchmark → 对比 → 诊断 → 出图。
3. 开发者能根据手册把自己的控制程序或算法接入平台，而不是靠读源码猜流程。
4. 平台至少有一组稳定的 2D/3D 标准实例可直接运行。
5. GUI 与主入口文档对系统能力的表述一致，不再延续旧阶段口径。
6. 过时内容有明确状态标注，后续维护规则可执行。

### 9.1 可量化验收指标

| 验收维度 | 指标 |
|----------|------|
| 文档 | README 显著收敛为轻入口页（当前 512 行）；系统主手册覆盖完整使用流程 |
| 实例 | 至少 4 个 2D 模板 + 4 个 3D 模板，每个模板真实可运行 |
| 接入指南 | 包含最小示例 + 完整示例 + 常见错误；覆盖临时加载和正式注册两种路径 |
| 工具手册 | 16 个工具全部有说明，按 6 类分组；研究工作流覆盖 6 步链路 |
| GUI | ATP 状态、obs_mode、target_type 三项缺失信息至少补齐其中的主状态显示；其中 ATP 状态如纳入本轮，需先完成状态暴露链路补齐 |
| 维护规则 | 维护检查清单至少覆盖 6 个维度（文档同步、工具新增、算法新增、实例新增、GUI 同步、阶段文档边界） |
