## 1. 实施原则

阶段6的关键不是"多写几份文档"，而是避免做出一套和当前仓库现状脱节的手册。因此本阶段按以下原则执行：

1. **先盘点，后整理**
   - 所有文档、实例、GUI、工具治理动作，都必须先以真实仓库现状为基线。

2. **先收口口径，再补内容**
   - 先解决"谁是主入口、谁是专项说明、谁是归档材料"的层级问题。

3. **先做可交付主链路，再做补充优化**
   - 优先保证"会用平台、会接入算法、会跑研究流程"这三条主链路跑通。

4. **对 GUI 做增量适配，不做推翻式改造**
   - 当前 GUI 已具备双轴与链路信息（yaw/pitch/u/v/backlog/obs_lag + 诊断面板三维坐标），应在现状基础上补齐真实缺口（ATP 状态、obs_mode、target_type）。

5. **对历史工具先标注再处置**
   - 未完成盘点前，不提前判定某工具一定废弃。

## 9. 风险与控制

### 风险 1：阶段6被做成"只补文档"

控制：
- 必须同时交付实例体系和维护规则，不能只写说明文字。
- 验收时每个场景模板必须真实可运行。

### 风险 2：误把已有能力当缺口，造成重复建设

控制：
- 把盘点清单设为前置 P0，不盘点不进入实施。
- 任务 C 的 GUI 差距表必须基于 `window.py` 代码行号确认。

### 风险 3：GUI 范围失控

控制：
- 先做差距表，后做增量更新；不承诺推翻式重构。
- 不对 GUI 修改行数做刚性承诺；以“范围小、链路清楚、不引入额外框架改造”为控制目标。
- ATP 状态若纳入 GUI，本轮实现需先确认状态如何从 control program 暴露到 snapshot，再决定是否当期实施。

### 风险 4：旧工具误判为废弃

控制：
- 所有"弃用"先经过盘点确认，再标注，不直接删除。
- 处理结果在工具矩阵表中留痕。

### 风险 5：实例模板写出来但跑不通

控制：
- 每个模板必须以真实命令运行验证，不能只停留在文档层面。
- 实施时每个模板先跑通再写入文档。

### 风险 6：README 收敛破坏现有入口

控制：
- README 收敛前，先完成系统主手册，确保 README 中移除的内容在新手册中有对应位置。
- 收敛后运行冒烟测试验证主入口仍然可用。
