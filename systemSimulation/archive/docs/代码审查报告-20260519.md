## 一、项目功能理解

当前项目不是单一算法脚本，而是一个完整的闭环仿真系统：

1. `DigitalTwinRuntime` 以固定 tick 顺序推进 `Target -> Gimbal -> Camera -> Raspi`
2. `Raspi` 侧控制程序通过图像观测生成命令，命令在下一 tick 生效
3. GUI 线程通过 `UiStateBuffer` 读取 worker 线程推送的快照、曲线和图像
4. 项目同时支持 `debug / research / realistic` 三种观测模式，以及离线、实时、工具脚本、测试基线等多种使用方式

因此，本次复核不只看静态代码，还结合了：

- 关键源码路径交叉核对
- 现有测试含义核对
- 实际运行验证
- 报告中结论与当前仓库状态是否一致的复查

## 二、复核结论总览

### 2.1 原报告中“确认成立”的问题

以下问题在当前代码中仍然成立，建议保留：

1. GUI 读取快照与曲线分两次加锁，存在跨 tick 混读风险
2. `get_next_search_rate()` 命名与实际副作用不一致
3. Raspi 控制程序直接复用 Camera 模块中的检测函数，模块边界偏紧
4. 全局配置对象为可变单例，存在跨运行污染风险
5. `metrics_log` / `event_log` 无上限，长时间 GUI 仿真会持续增长
6. Runtime 丢弃了 `_dispatch()` 的返回结果，命令失败时缺乏反馈
7. `_on_apply_delay`、`ControlProgramFactory`、`ScheduledItem` 属于遗留/死代码
8. 航点解析处存在死代码和重复逻辑
9. `GimbalEntity.get_state()` 通过 `update(0.0, ...)` 读取状态，语义上有副作用
10. `Command` 缺少运行时合法性校验
11. `state_buffer._extract_detection()` 阈值硬编码为 180，与配置不一致
12. `obs_filter._copy_frame()` 对未知类型直接原样返回，不满足“隔离原始数据”的约束
13. `bootstrap.py` 中等待 READY 的 3200 为无说明魔法数字

### 2.2 原报告中“结论不准确或已失效”的问题

以下条目不建议继续按原表述保留：

1. **延时预算超过 100%**
   当前 `apply_delay_profile()` 的注释已经明确把观测读取阶段视为并行关系，实际总观测延时按 `max(image_read, state_read) + process + command_tx` 计算。以 `100ms` 验证时，配置为 `25ms / 50ms / 25ms / 25ms`，总链路等于 `25 + 50 + 25 = 100ms`，不是 125%。

2. **ATP 搜索扫描 off-by-one**
   代码写法确实容易让人误读，但现有测试和实际序列都没有证明“驻留帧数少 1”。该问题目前更像“实现可读性差”，不宜继续定性为已确认 bug。

3. **`CameraConfig` 缺少 `cy`**
   这是接口对称性建议，不是明确缺陷；当前相机内参与使用点都通过 `intrinsics["cy"]` 或直接按高度计算，暂未造成行为错误。

4. **`read_curves()` 返回 7 元素元组**
   这是可维护性建议，不是问题本身；当前调用方数量有限且位置含义稳定，优先级不高。

5. **未使用导入列表**
   其中部分条目已经不准确，不能直接照搬原清单。

## 三、严重问题（建议优先修复）

### 3.1 GUI 状态读取不是同一时刻快照

**文件**: `simulation/gui/window.py`、`simulation/state_buffer.py`

**问题**:  
`_render_tick()` 先调用 `read_latest()`，再调用 `read_curves()`。两次读取之间 worker 线程可能刚好 `push()` 新数据，导致：

- 世界视图、相机面板用的是新快照
- 时间轴曲线用的是旧历史，或反过来

这种不一致不会每次都出现，但一旦出现，界面会表现为闪动、标签和曲线对不上、某些帧的 ATP 状态和误差曲线错位。

**修改方案**:

1. 在 `UiStateBuffer` 中增加一次性读取接口，如 `read_all()`
2. 单次加锁返回 `snapshot / frame / curves / logs` 中需要的组合
3. GUI 渲染只使用这份原子快照

---

### 3.2 相机帧对象直接暴露，外部可修改内部数据

**文件**: `entities/camera/entity.py`、`runtime/digital_twin_runtime.py`、`simulation/worker.py`

**问题**:  
`CameraEntity.get_frame()` 直接返回内部保存的 `last_frame`。我已实际验证：

- 取出返回值后修改 `frame.image[0,0]`
- 再次读取 `get_frame()`
- 内部帧数据已被外部改写

这意味着 GUI、控制程序或调试脚本如果误改返回帧，会直接污染运行中的相机输出，属于真实的数据隔离缺陷。

**修改方案**:

1. `CameraEntity.get_frame()` 返回深拷贝或轻量不可变副本
2. `DigitalTwinRuntime._get_camera_frame()` 也应只暴露副本
3. 若担心复制成本，至少复制 `image` 和 `intrinsics`，禁止直接回传内部引用

---

### 3.3 `get_next_search_rate()` 名称误导，且会推进内部扫描状态

**文件**: `entities/raspi/atp_state_machine.py`

**问题**:  
方法名像“读取当前搜索速率”，但实际会推进：

- `_search_dwell_count`
- `_search_yaw_deg`
- `_search_pitch_deg`
- `_search_pitch_stepping`

一旦同一 tick 被额外调用一次，扫描状态就会被推进两次。这个风险在调试、GUI 展示、后续重构中很容易踩到。

**修改方案**:

1. 改名为 `advance_search_step()` 或 `step_search_scan()`
2. 给调用方约束“每个控制 tick 只能调用一次”
3. 最好补一条测试，防止未来又被当成纯 getter 使用

---

### 3.4 Raspi 与 Camera 检测逻辑耦合过深

**文件**:  
`entities/raspi/tracker_program.py`  
`entities/raspi/atp_control_program.py`  
`entities/raspi/trackers/*.py`

**问题**:  
多个 Raspi 控制程序直接从 `entities.camera.entity` 导入 `detect_beacon_centroid`。这会带来两个问题：

1. 控制算法依赖相机实体内部实现，而不是依赖清晰的观测接口
2. 以后只要相机模块重构、移动函数、替换检测策略，Raspi 侧就会被连带牵动

这不一定立刻出错，但对后续扩展不同检测器、不同相机模型、不同观测格式很不友好。

**修改方案**:

1. 抽到独立公共模块，例如 `simulation/detection.py`
2. 或让观测层直接提供检测结果，控制程序只消费观测，不自己 import 相机实现

## 四、中等问题（建议近期修复）

### 4.1 全局配置对象可变，跨运行会互相污染

**文件**: `config.py`、`simulation/headless.py`、`simulation/bootstrap.py`

**问题**:  
当前大量模块级 `*_cfg` 对象会被直接修改，例如目标运动类型、航点、观测模式等。这样会导致：

- 同一进程里连续跑两次仿真，第二次继承第一次残留
- GUI reset 后不一定真的回到“默认”
- 测试之间需要靠人为小心，隔离性差

**修改方案**:

1. 短期在 `build_runtime()` 时复制配置
2. 长期改成工厂函数，每次构造 runtime 都拿一份新配置实例

---

### 4.2 `metrics_log` / `event_log` 无上限增长

**文件**: `simulation/state_buffer.py`

**问题**:  
曲线历史已经用 `deque(maxlen=...)` 限制了长度，但导出用的两份日志还是无限列表。长时间运行 GUI 时会不断占内存。

**修改方案**:

1. 改为 `deque(maxlen=N)`
2. 或按导出需求定期截断

建议：

- `metrics_log` 保留最近 60 秒或用户配置窗口
- `event_log` 保留最近 1000 条左右

---

### 4.3 Runtime 丢弃命令执行结果

**文件**: `runtime/digital_twin_runtime.py`

**问题**:  
`_apply_due_commands()` 调用了 `_dispatch()`，但返回的 `CommandResult` 没有记录、没有日志、没有事件。命令如果被拒绝，外层几乎无从得知。

**修改方案**:

1. 至少增加 debug 日志
2. 更好的是把失败事件放进快照或导出日志

---

### 4.4 `GimbalEntity.get_state()` 读取状态时带副作用

**文件**: `entities/gimbal/entity.py`

**问题**:  
`get_state(timestamp)` 通过 `update(0.0, timestamp)` 获取状态。虽然 `dt=0` 不会推进物理角度，但会再走一遍控制器逻辑并刷新 `_last_ctrl`，和“纯读取”语义不一致。

**修改方案**:

1. 缓存最近一次 `update()` 的结果
2. `get_state()` 只返回缓存，不再触发控制器 step

---

### 4.5 航点解析逻辑重复且含死代码

**文件**: `entities/target/model.py`

**问题**:

1. `_step_waypoint()` 开头那行四元解析会立刻被下面分支覆盖
2. 同一段“3 元/4 元航点”解析逻辑写了两遍

这类问题短期不一定炸，但很容易在后续改航点格式时改漏一处。

**修改方案**:

1. 删除无效初始化
2. 提取 `_parse_waypoint()`

---

### 4.6 死代码和遗留代码仍在主路径附近

**文件**:

- `simulation/gui/window.py` 的 `_on_apply_delay`
- `simulation/bootstrap.py` 的 `ControlProgramFactory`
- `entities/raspi/delay_pipeline.py` 的 `ScheduledItem`

**问题**:  
这些代码不会直接造成行为错误，但会干扰后续审查、误导维护者理解当前活跃实现。

**修改方案**:

1. 删除无引用代码
2. 如果暂时保留遗留文件，至少在文件头明确标注“遗留，不参与运行”

---

### 4.7 观测复制边界不彻底

**文件**: `simulation/obs_filter.py`

**问题**:  
`_copy_frame()` 对已知 `FramePacket` 会复制图像并剥离真值，但对未知对象类型直接原样返回。这和函数注释里“避免修改原始数据”的承诺不一致。

**修改方案**:

1. 对 fallback 使用 `copy.deepcopy`
2. 或直接抛错，让调用方显式适配

## 六、新增发现的问题

### 6.1 `debug` 观测模式直接透传原始 `world_obs`

**文件**: `simulation/obs_filter.py`

**问题**:  
`debug` 模式直接 `return world_obs`，也就是把 runtime 内部使用的观测对象整体暴露给控制程序。虽然当前控制程序没有主动写回，但接口层面没有任何保护。

这和上面的“相机帧可被外部改写”问题叠加后，会让 debug 模式下的控制程序天然拥有修改内部运行对象的能力。

**修改方案**:

1. 即使在 `debug` 模式，也返回隔离后的副本
2. 至少对 `frame` 做复制，对字典做浅/深拷贝

---

### 6.2 `camera_client.get_frame()` 读取链路没有统一走 runtime 锁

**文件**: `runtime/digital_twin_runtime.py`、`simulation/worker.py`

**问题**:  
worker 线程在 `runtime.step(1)` 之后又单独调用一次 `camera_client.get_frame()`，这次读取没有通过 runtime 快照绑定在同一锁内。虽然当前大部分情况下仍是同一线程执行，但接口语义上已经允许“快照来自一步，图像来自另一次读取”。

这比 3.1 的 GUI 竞态更轻，但同样属于快照边界不严的问题。

**修改方案**:

1. 在 `step()` 返回值中直接携带对应用帧副本
2. 或提供“快照 + 帧”统一读取接口，避免二次取数

## 十、Claude Code 二次复核意见（2026-05-19）

### 10.1 对 Codex 复核结论的确认

逐条核对源码后，Codex 的复核结论整体准确：

1. **延时 125% 降级** — 确认正确。`raspi/model.py` L135 中 `obs_delay = max(image_read, state_read)`，实际链路为 `max(25,25) + 50 + 25 = 100ms`，并行模型下总延时等于用户指定值。原报告此条确实误判。

2. **ATP off-by-one 降级** — 确认合理。L254 设置 `_search_pitch_stepping = search_dwell_frames` 后 L257-260 同帧递减，确实会少一帧，但这更像"实现可读性差"而非已证实的行为错误（取决于设计意图是"发送 N 帧"还是"驻留 N 个周期"）。降为可读性问题合理。

3. **相机帧外部可修改** — 确认真实存在。`CameraEntity.get_frame()` (L192-193) 直接 `return self.last_frame`，numpy array 是可变引用。

4. **debug 模式透传 world_obs** — 确认真实存在。`obs_filter.py` L67-68 直接返回原始字典引用。

5. **camera_client.get_frame() 无锁** — 确认存在。`worker.py` L76 在 `step()` 之后单独调用，不在同一锁内。

### 10.2 Codex 复核中的一个小瑕疵

Codex 在 6.1 节说"debug 模式下控制程序天然拥有修改内部运行对象的能力"——这个结论需要细化：

- `world_obs` 是在 `runtime.step()` 内部每 tick 新构建的临时字典（`digital_twin_runtime.py` L108-114）
- 字典本身是新建的，但其中 `target`/`gimbal`/`camera` 的值来自 `state.__dict__`，而 `__dict__` 返回的是属性字典的引用
- 因此控制程序如果修改 `obs["gimbal"]["yaw_deg_internal"] = 999`，**不会**影响 gimbal 实体内部状态（因为 `__dict__` 是 dataclass 实例的属性字典副本）
- 但 `obs["frame"]` 是 `self.last_frame` 的直接引用，修改 `obs["frame"].image` **会**污染相机内部数据

所以 6.1 的风险范围比 Codex 描述的略窄：只有 `frame` 字段存在真实的反向污染风险，`target/gimbal/camera` 字典修改不会回传。但 `frame` 这一条已经足够严重。

### 10.3 新增发现的问题

以下是 Codex 复核中未覆盖的额外问题：

#### 10.3.1 `_on_reset` 不等待旧 worker 线程完全退出即创建新 runtime

**文件**: `simulation/gui/window.py` L528-543

**问题**:  
`_on_reset()` 调用 `self.worker.wait(2000)` 后立即创建新 runtime 和新 worker。但 `wait(2000)` 有超时——如果旧线程 2 秒内未退出（例如卡在一次耗时的 `step()` 中），新旧 worker 会短暂并存，两个线程同时操作不同 runtime 实例写入同一个 `state_buf`。

虽然 `state_buf.clear()` 在新 worker 创建前调用，但如果旧线程在 clear 之后、新 worker start 之前还推了一帧数据，就会出现脏数据。

**修改方案**:  
1. `wait()` 后检查 `isRunning()`，若仍在运行则强制终止或跳过 reset
2. 或在 `SimWorker.run()` 中检查 stop_flag 的粒度更细（当前每个 step 后才检查）

---

#### 10.3.2 `_draw_timeline` 中 ATP 区域每帧全量重建

**文件**: `simulation/gui/window.py` L803-829

**问题**:  
每次 `_render_tick`（30Hz）都会：
1. 遍历所有旧 `LinearRegionItem` 并 `removeItem`
2. 清空列表
3. 重新扫描整个 `atp_windowed` 数组创建新 region

对于 5 秒窗口 @ 200Hz = 1000 个数据点，每帧都做 O(n) 扫描 + 创建/销毁 Qt 图形对象。这是 GUI 性能的潜在瓶颈，尤其在长 `plot_window_s` 配置下。

**修改方案**:  
增量更新：只在 ATP 状态发生变迁时添加新 region，只移除滑出时间窗口的旧 region。

#### 10.3.3 `_atp_windowed` 索引逻辑脆弱

**文件**: `simulation/gui/window.py` L761

```python
atp_windowed = [atp_state_list[i] for i in range(len(mask)) if mask[i]]
```

**问题**:  
`mask` 是对 `t_np` 的布尔索引（L756），而 `atp_state_list` 是原始长度的 list。这里用 `range(len(mask))` 遍历 `mask`（它是 numpy array，`len(mask)` = 原始长度），然后用 `mask[i]` 过滤。逻辑上等价于 `np.array(atp_state_list)[mask]`，但：

- 如果 `atp_state_list` 和 `t_np` 长度不一致（理论上不应该，但 `read_curves()` 分两次锁读取时可能出现），会产生 `IndexError` 或静默截断
- 这与 3.1 的竞态问题叠加：如果 `read_latest()` 和 `read_curves()` 之间有新数据推入，`atp_state_list` 可能比 `t_np` 多一个元素

**修改方案**:  
统一使用 `read_all()` 原子读取后，此问题自然消除。短期可加 `min(len(mask), len(atp_state_list))` 防御。

#### 10.3.6 `RaspiEntity.set_delay_profile` 修改全局单例配置

**文件**: `entities/raspi/entity.py` L74-95

**问题**:  
`set_delay_profile()` 通过 `setattr(self.delay_cfg, k, ...)` 直接修改 `self.delay_cfg`。如果 `self.delay_cfg` 是全局 `raspi_delay_cfg`（构造时未传入自定义 cfg 的情况），则修改会泄漏到全局。这是 4.1 全局单例问题的一个具体表现：

```python
# 构造时：
self.delay_cfg = delay_cfg or raspi_delay_cfg  # 可能拿到全局引用
# set_delay_profile 时：
setattr(self.delay_cfg, k, ...)  # 直接修改全局对象
```

GUI reset 后新建的 RaspiEntity 会继承上一次修改过的全局配置。

**修改方案**:  
构造时 `self.delay_cfg = copy.deepcopy(delay_cfg or raspi_delay_cfg)`，确保每个实体持有独立副本。

#### 10.3.7 手动导出摘要时算法名称可能写错

**文件**: `simulation/gui/window.py` L548-564

**问题**:  
`_on_save()` 导出 `summary.json` 时，`control_program` 字段使用的是：

```python
"control_program": self.cfg.control_program_path or "BaselineTrackerProgram",
```

这会导致两类错误：

1. 如果用户通过下拉切换了算法，但 `control_program_path` 为空，导出结果仍会写成 `BaselineTrackerProgram`
2. 实际运行中的算法来源优先级已经变成“下拉覆盖优先，其次才是路径加载”，但导出摘要没有跟这个规则保持一致

所以导出的摘要文件可能和当时界面上实际运行的算法不一致。

**修改方案**:  
导出时复用与 `_build_control_program()` 一致的口径，优先记录 `self._algo_key_override`，其次再回退到 `self.cfg.control_program_path`。
