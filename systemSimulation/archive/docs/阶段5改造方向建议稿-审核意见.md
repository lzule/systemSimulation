## 3. 需要调整的部分

### 3.1 优先级应更鲜明

Codex 的四个方向是平铺的，但实际上价值差异很大。建议按以下优先级排序：

| 优先级 | 方向 | 理由 |
|--------|------|------|
| **P0 必做** | A. 结果回归对比 | 直接回答"这次改动有没有变好"，这是算法迭代的核心反馈环 |
| **P1 应做** | C. 实验记录模板 | 成本低、收益高，避免实验过程不可追溯 |
| **P2 选做** | B. 结果展示增强 | 当前 CSV/JSON + matplotlib 已可用，Excel 导出是锦上添花 |
| **P3 自然形成** | D. 研究流程固化 | 这是A+C做好后自然产生的结果，不应单独作为开发方向 |

**方向D的问题**：Codex 把"研究流程固化"列为独立方向，但流程固化不是写出来的，是用出来的。如果A和C做对了，D会自然形成。如果把D当成独立开发任务，容易变成"写规范文档"而非"建实际能力"。建议将D的内容拆散融入A和C。

### 3.2 缺少"算法诊断"能力

这是 Codex 方向稿中最大的缺漏。

当前 benchmark 结果显示：
- atp_search_track_baseline: 20.31 px
- baseline_rate_p: 20.33 px
- rate_pi: 20.63 px
- alpha_beta: **56.85 px**（差 2.8x）
- linear_kf: **142.47 px**（差 7x）

预测器性能差距这么大，**不是参数微调能解决的，大概率是算法本身有问题（输入不对、状态空间不对、或者增益设置不合理）**。

仅靠 RMS 数值比较无法诊断这种问题。需要：
- **误差时间序列对比**：当前已有 error_curve.png，但只支持单次实验，缺少跨算法叠加对比
- **ATP 状态转换时间线对比**：不同算法在什么时间点进入/退出跟踪状态
- **逐时段误差分解**：捕获阶段 vs 稳态跟踪阶段 vs 失锁阶段的误差分别多少
- **预测量 vs 实际量的偏差分析**：预测器输出与真值的逐点对比

建议在方向A中增加"算法诊断"子功能，优先级与回归对比同等。

### 3.3 缺少"实验批次管理"

75 组实验已经需要 3 路并行约 20 分钟。后续如果加入更多算法（你已提到后续可能有新算法开发需求）、更多场景、更多种子，实验规模会快速增长。

当前管理方式是手动执行 `run_benchmark.py` + `summarize_results.py`，缺少：
- **实验批次标记**：这批实验是为了验证什么改动而跑的
- **批次间的结果继承**：新批次能否复用历史基线结果，而非每次全部重跑
- **增量实验**：只跑新增的算法/场景组合，而非每次全量重跑

这部分建议作为方向A的附属能力，不需要单独成方向。

### 3.4 方向B应更务实

Codex 对方向B的描述偏理想化（"更适合研究使用的对比输出""导出为 Excel"）。当前已有：
- `summary.csv` + `summary_grouped.csv`（可直接用 Excel 打开）
- `summary.json`（结构化数据）
- 控制台排名表

真正缺的不是更多输出格式，而是**跨算法的对比图**。比如：
- 同一场景下 5 种算法的误差曲线叠加图
- 算法排名雷达图（多指标综合对比）
- 算法性能 vs 场景难度热力图

建议方向B聚焦在"对比可视化"，而不是"格式转换"。

## 4. 对四个核心需求评估的补充

Codex 在第7节列了三个需求，我认为还缺一个：

### 4.4 需求四：能诊断算法为什么失败

当前已有需求一（比较谁更好）、需求二（看过程）、需求三（支持后续扩展）。

但缺少：**当某个算法明显不如基线时，能快速定位原因。**

这不是回归对比（那只告诉你"差了多少"），而是**根因分析**。具体需要：
- 预测器输出与真值的逐点偏差（当前 benchmark 不记录这个）
- 控制器输入/输出的时间序列（当前也不记录）
- ATP 状态转换原因标注（是因为误差超阈值？还是预测发散？）

这个需求应该在方向A中体现。

## 5. 对"边界区分"的补充

Codex 在第6节区分了阶段4和阶段5的边界，区分是对的，但还可以更具体：

**阶段4已交付的：**
- 5 种算法的 benchmark 适配
- `run_benchmark.py`（批量运行）
- `summarize_results.py`（汇总+排名）
- 75 组正式结果
- 每组结果含 result.json / metrics.csv / error_curve.png / state_timeline.png / notes.md

**阶段5不应重做的：**
- 不重新设计 benchmark 运行流程
- 不修改已有的 result.json 输出格式
- 不重写汇总逻辑

**阶段5应新增的：**
- 在已有输出格式基础上增加对比层
- 在已有工具链上增加诊断和回归能力
- 新增实验记录规范

## 6. 建议的最终阶段5定义

基于以上分析，建议阶段5定义为：

**阶段5：研究支撑与结果固化**

核心目标：让算法迭代形成可闭环、可追溯、可对比的研究工作流。

### 任务拆分（4项）

| # | 任务 | 交付物 | 优先级 |
|---|------|--------|--------|
| 1 | **回归对比与算法诊断工具** | `tools/compare_results.py`：选定基线组 vs 新组自动对比，输出差异表 + 退化报警；`tools/diagnose_algorithm.py`：误差分时段统计 + ATP 状态转换对比 + 预测偏差分析 | P0 |
| 2 | **实验记录模板** | 每次实验批次自动生成 `experiment_log.md`，固定记录实验目标、改动内容、运行命令、关键结果、结论；工具侧在 `run_benchmark.py` 增加 `--experiment-note` 参数 | P1 |
| 3 | **对比可视化** | `tools/plot_comparison.py`：跨算法误差曲线叠加、多指标排名雷达图、算法×场景热力图；基于已有 result.json 数据 | P2 |
| 4 | **增量实验支持** | `run_benchmark.py` 增加 `--skip-existing` 参数，跳过已有结果的组合；`--baseline-tag` 标记基线批次供后续对比 | P2 |

### 不做的

- 不新增算法框架
- 不修改底层模型
- 不做论文写作系统
- 不做通信链路建模
- 不做重型实验管理平台

### 闸门条件（建议）

- [ ] 能指定两组实验结果自动对比，输出差异表和退化项
- [ ] 能自动生成实验批次的记录文件
- [ ] 能生成至少一种跨算法对比图
- [ ] 增量实验不重复跑已有结果

## 7. 对 Codex 建议稿本身的评价

### 优点
- 诊断准确（原阶段5太宽）
- 边界清晰（阶段4 vs 阶段5 vs 不属于阶段5）
- 目标明确（服务研究效率和研究可信度）
- 排除列表合理

### 不足
- **篇幅过长**：14节中大量是论证和说服性内容，核心决策点可以在5节内说完。建议稿本身也需要"固化"
- **优先级不明确**：四个方向平铺，实际价值差异大
- **缺少"诊断"视角**：只关注"比较结果"，不关注"理解原因"
- **方向D定义不清**：容易滑向"写流程文档"
- **对已有能力评估不足**：没有详细列出阶段4已交付了什么，导致阶段5的增量不够清晰

### 风险提示

如果完全按 Codex 建议稿执行，主要风险是：
1. 方向D可能变成纯文档工作，产出不可验证
2. 缺少诊断能力导致：发现问题（谁差了）→ 无法解释（为什么差）→ 反复试错
3. 方向B可能做成格式转换工具而非研究工具

## 8. 最终建议

1. **采纳 Codex 的方向判断**：保留阶段5、改写内容、定位为研究支撑
2. **调整优先级**：A > C > B，D 拆散融入 A/C
3. **补充"算法诊断"能力**：作为方向A的核心子功能
4. **控制范围**：4项具体交付物，不做泛化平台工作
