### 1.2 Codex 遗漏或判断不够准确的部分

**遗漏 1：Kp 参数不一致 bug（严重）**

Codex 完全没有发现：`TrackerTuningConfig`（config.py:93）默认 Kp=1.1，而 `TrackerTuning`（tracker_program.py:16）默认 Kp=0.08，差 13.75 倍。`build_runtime()` 走的是 config 路径（1.1），但 `tune_tracker_kp.py` 和 `run_raspi_tracking_demo.py` 走的是 `TrackerTuning` 默认值（0.08）。这意味着扫参工具的基准和运行时的基准是不同的。

**遗漏 2：死代码 `delay_pipeline.py` 未被任何代码引用**

Codex 提到 Raspi 模型已改为单槽状态机，但没指出 `delay_pipeline.py` 中的 `DelayPipeline` 类已经完全没有被 import，成了纯粹的死代码。

**遗漏 3：相机模型实际上是 1D 的**

Codex 说"v 基本固定在中线"，但没有明确指出这是**硬编码行为**（model.py:31 `v = h / 2.0`），不是"基本"而是"永远"。这意味着尽管系统有双轴云台，跟踪回路实际上是**纯 1 轴**的。Pitch 控制存在但没有视觉反馈，pitch_rate 始终发 0。

**遗漏 4：Raspi jitter 分布有系统性正偏**

entity.py:84 `max(0.0, random.gauss(0.0, std))` 截断了负值，导致延迟分布不是对称高斯而是右偏半高斯。E[jitter] = std × sqrt(2/π) ≈ 0.8×std，不是 0。这意味着实际平均延迟比配置值偏高。

**遗漏 5：多个关键参数未进入 config**

- GimbalEntity.boot_delay_s = 1.5（硬编码在 entity.py:53）
- CameraEntity.boot_delay_s = 0.5（硬编码在 entity.py:42）
- ZoomController tau_s=0.2, max_rate_mmps=120.0（硬编码在 entity.py:48）
- 高斯 blob sigma=3.2（硬编码在 model.py:36）
- 检测阈值 threshold=180（硬编码在 entity.py:28）

这些都不在 config.py 中，无法通过 config_editor 或命令行修改。

**遗漏 6：`apply_delay_profile()` 分配逻辑有计算问题**

bootstrap.py:26-32 中，`image_read`、`state_read`、`command_tx` 各分 25%，加 `image_process` 50%，总计 125%。但实体实际使用 `max(image_read, state_read)`（entity.py:99），所以端到端延迟是 `max(25%,25%) + 50% + 25% = 100%`，这恰好正确——但代码的意图不清晰，总分配量超过 100% 依赖 `max()` 的隐式逻辑来修正。

**遗漏 7：无端到端闭环集成测试**

226 个测试全部是单元级和模块级。没有任何测试验证"目标运动→云台跟踪→相机成像→Raspi 控制→命令回到云台"的完整闭环稳态跟踪误差。这是一个测试覆盖上的重要缺口。

### 3. 模型与物理真实性

#### 3.1 Target 模型 — 运动学评价

**模型本质**：二维平面点目标，5 种运动模式（正弦、匀速、匀加速、随机游走、航点）。

**真实性评估**：

| 方面 | 当前状态 | 与真实世界的差距 |
|------|---------|----------------|
| 维度 | 2D (x,y) | 真实目标有高度 z、俯仰角、横滚角 |
| 尺寸 | 点目标 | 真实目标有物理尺寸，影响成像大小和遮挡 |
| 动力学 | 运动学方程 | 真实无人机/车辆有惯性、气动力、最大加速度约束 |
| 正弦模式 | 精确解析解 | 好的设计，无积分误差 |
| 匀加速模式 | 前向 Euler 积分 | dt=5ms 下误差可忽略，但方法不够优雅 |
| 随机游走 | uniform 加速度 + 阻尼 | 真实机动更接近 Ornstein-Uhlenbeck 过程或转弯率模型 |
| 航点 | 到达后瞬移 | 应改为平滑减速停止 |

**对科研的影响**：
- 2D 运动足够支撑"水平跟踪算法验证"类研究
- 若要支撑"真实场景跟踪"类论文，必须升到 3D 并增加动力学约束
- 正弦模式是最适合做对照实验的（确定性、可复现）

#### 3.2 Gimbal 模型 — 动力学评价

**模型本质**：一阶惯性环节 `rate_actual = (1-α)×rate_actual + α×rate_cmd`，τ=30ms。

**真实性评估**：

| 真实云台特性 | 当前是否建模 | 影响程度 |
|-------------|------------|---------|
| 电机惯量 J | ❌ | 高 — 决定带宽和响应形态 |
| 电机力矩常数 Kt | ❌ | 高 — 决定加速度能力 |
| 反电动势 | ❌ | 中 — 影响高速时的力矩衰减 |
| 库仑摩擦 + 静摩擦 | ❌ | 高 — 导致低速爬行和死区 |
| 齿隙/反向间隙 | ❌ | 中 — 导致位置振荡 |
| 结构共振 | ❌ | 中 — 限制控制器增益上限 |
| 编码器量化噪声 | ❌ | 中 — 影响低速控制精度 |
| 偏置/漂移 | ❌ | 低 — 长时间运行影响 |
| 陀螺仪耦合 | ❌ | 低 — 双轴耦合效应 |
| 驱动饱和 | ✅ (rate clamp) | 已有限幅 |
| Pitch 硬限位 | ✅ | 已实现，但无反弹 |

**关键判断**：当前云台模型是**速率指令低通滤波器**，不是真正的动力学模型。τ=30ms 对应 -3dB 带宽约 5.3Hz，这在真实云台的 2-20Hz 范围内偏低但合理。

**对科研的影响**：
- 对"控制策略比较"类研究足够（不同 Kp/Ki 的相对性能排序是对的）
- 对"绝对性能指标"类研究不够（RMS=0.8° 不能直接声称在真实硬件上也是 0.8°）
- 若要做"鲁棒控制"研究，必须引入参数不确定性和非理想因素

#### 3.3 Camera 模型 — 成像评价

**模型本质**：针孔投影 + 高斯亮点渲染（σ=3.2px）+ 高斯噪声（σ=2.0）。

**核心问题：系统是 1 轴的**

```python
# model.py:31
v = h / 2.0  # 目标永远在图像垂直中心
```

```python
# tracker_program.py:130
pitch_rate=0.0  # Pitch 速率永远为 0
```

这意味着：
- v 坐标恒等于 cy，不存在 v 方向像素误差
- Pitch 轴没有任何视觉反馈驱动
- 系统实质上是 **1 轴水平跟踪系统**，尽管有 2 轴云台硬件

**真实性评估**：

| 真实相机特性 | 当前是否建模 | 对研究的影响 |
|-------------|------------|-------------|
| 镜头畸变（径向/切向） | ❌ | 中 — 边缘区域误差增大 |
| 运动模糊 | ❌ | 高 — 快速运动时真实图像会模糊 |
| 曝光时间/自动曝光 | ❌ | 低 — 当前场景亮度固定 |
| 滚动快门 | ❌ | 中 — 快速运动导致图像畸变 |
| 读出噪声/暗电流 | ❌ | 低 — 对质心检测影响小 |
| 散粒噪声（泊松） | ❌ | 中 — 信号相关噪声 |
| 目标外观模型 | 高斯亮点 | 极高 — 真实目标不是高斯亮点 |
| 目标大小随距离变化 | ❌ | 高 — σ=3.2 是固定的 |
| 背景/杂波 | ❌ | 极高 — 黑底 + 单亮点是最简单场景 |
| 多目标/遮挡 | ❌ | 高 — 真实场景常见 |

**检测算法评估**：

```python
# entity.py:28-35
def detect_beacon_centroid(image, threshold=180):
    ys, xs = np.where(image >= threshold)
    cx = float(xs.mean())
```

这是最简单的阈值分割+质心提取。在当前黑底+高斯亮点场景下完美工作，但在任何真实场景中都会失败。阈值 180 是硬编码的。

**对科研的影响**：
- 当前图像过于理想，算法效果会被高估
- 跟踪 RMS=0.8° 的结果不能泛化到真实场景
- 如果要做"视觉算法研究"，必须至少增加：距离相关目标大小、随机亮度变化、偶发丢检

#### 3.4 Raspi 模型 — 延时链路评价

**模型本质**：单槽忙/闲状态机（IDLE→READING→PROCESSING→SENDING→IDLE），空闲抓最新帧，忙时跳过。

**真实性评估**：

| 真实嵌入式视觉特性 | 当前是否建模 |
|-------------------|------------|
| 帧缓冲（1-3帧） | ❌ — 只保留 0 或 1 |
| 处理时间随场景变化 | ❌ — 固定 + 小抖动 |
| 丢帧计数器 | ❌ — 没有统计丢帧率 |
| 串口/CAN 通信延迟分布 | ❌ — 固定延迟 |
| 网络丢包/重传 | ❌ |
| 内存带宽竞争 | ❌ |
| CPU 调度抖动 | 部分 — 通过 jitter 近似 |

**核心判断**：单槽最新帧模型对某些嵌入式视觉系统是合理的（如 OpenMV、低帧率 CMOS），但不代表所有系统。当前系统缺少其他处理策略的选项。

#### 3.5 闭环时序分析

```
Tick (5ms):
  Target.update()         ← 0μs  产生世界状态
  Gimbal.update()         ← ~0μs 执行上一 tick 的命令
  Camera.update()         ← ~0μs 根据当前世界状态成像
  Raspi.update()          ← ~0μs 可能看到 n ticks 前的帧
    └─ command submit     ← 命令被延迟若干 ticks 后生效
```

**关键观察**：
1. 所有实体的 `update()` 在同一个 tick 内顺序执行，但 Camera 看到的是"同一时刻"的 Target 和 Gimbal 状态——这意味着**感知延时为零**（除了 Raspi 引入的管线延时）。
2. 命令在 `apply_at = timestamp + runtime_dt` 生效，即最少 1 个 tick（5ms）的命令执行延迟。
3. 总闭环延时 = Raspi 管线延时（~23ms）+ 命令执行延迟（5ms）= ~28ms，即约 5-6 个 tick。

**与真实系统的差距**：
- 真实系统中，相机曝光、图像传输、特征提取、控制计算、串口通信每一步都有独立延时
- 真实系统中各环节可能不同步（相机 30fps、控制器 200Hz、电机驱动 20kHz）
- 当前系统所有环节同步于统一 dt=5ms 时钟

### 4. 系统配合与方法论

#### 4.1 观测泄漏问题（核心方法论问题）

当前 `ControlProgram.on_tick(obs)` 收到的 `obs` 字典包含：

```python
{
    "timestamp": ...,
    "target": {  # ← 真值！
        "x_m": ..., "y_m": ..., "vx_mps": ..., "vy_mps": ...,
        "bearing_deg": ..., "distance_m": ...
    },
    "gimbal": {  # ← 真值！
        "yaw_deg_internal": ..., "pitch_deg": ...,
        "yaw_rate_dps": ..., "pitch_rate_dps": ...
    },
    "camera": {  # ← 真值！
        "f_current_mm": ..., "in_fov": ..., "u_px": ..., "v_px": ...
    },
    "frame": FramePacket(...)  # ← 唯一的"传感器"输入
}
```

`BaselineTrackerProgram` **只使用了 `frame` 和 `gimbal.mode`**（用于切换 RATE_MODE），没有直接使用 target/gimbal 真值——这是好的。但：
- 控制程序**可以**访问所有真值，没有任何机制阻止
- 未来如果有人写了"聪明的"控制程序，很可能不知不觉地使用了 `obs["target"]` 来做预测
- 论文中声称"纯视觉闭环"但实际上用了真值，会产生虚假的性能提升

**建议**：实现 `obs_filter` 层，根据运行模式过滤 obs 字典：
- `debug` 模式：全部透传
- `vision_only` 模式：只保留 frame + gimbal.mode
- `realistic` 模式：frame + 有噪声的 gimbal 状态 + 无 target

#### 4.2 缺少统一评价体系

当前系统缺少以下实验基础设施：

| 缺失项 | 说明 |
|--------|------|
| 标准化实验脚本 | 每次实验需要手动写 headless 运行 + 统计 |
| 统一指标计算 | 没有"给定世界快照序列，输出标准指标"的工具 |
| 实验结果记录格式 | 没有标准化的 JSON/CSV 实验输出格式 |
| 基准结果数据库 | 无法对比"上次改动前的性能" |
| 统计显著性检验 | 没有"跑 30 次取均值 ± 标准差"的自动化 |

**建议的核心指标**：

```python
metrics = {
    "tracking_rate": ...,        # 跟踪成功率（in_fov 的比例）
    "mean_pixel_error": ...,     # 平均像素误差
    "rms_angle_error_deg": ...,  # 角度误差 RMS
    "peak_error_deg": ...,       # 峰值误差
    "settling_time_s": ...,      # 进入 ±2° 以内的时间
    "lost_count": ...,           # 丢失目标次数
    "mean_recovery_s": ...,      # 平均恢复时间
}
```

### 6. 物理世界真实性对照表

#### 6.1 各模块真实性评分
