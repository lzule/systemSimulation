## 1. 本阶段要解决什么

阶段 3 已经完成双轴几何升级、近真实成像、观测模式分层、云台非理想项和延时策略扩展。当前平台已经具备：

1. 在 `debug / research / realistic` 三种观测模式下运行控制程序
2. 在近真实条件下对同一算法做可复现的退化对比
3. 在不改底层模型的前提下，继续把研究重心转移到 **树莓派侧决策与控制算法**

因此，阶段 4 的核心目标是：

**把当前平台从“能跑一个基线控制器”升级为“能公平比较一组树莓派侧 ATP 算法基线”的研究平台。**

这一步主要解决四类问题：

1. 当前只有一个默认跟踪器，缺少可比较的算法池
2. 当前没有 ATP 状态机，捕获 / 粗跟踪 / 精跟踪 / 失锁 / 重捕获概念尚未落地
3. 当前缺少统一 benchmark 流程，算法结果难以横向比较
4. 当前缺少标准化的阶段 4 实验输出，无法稳定产出排序结论

---

## 2. 为什么主要在树莓派程序层完成

阶段 4 默认以 **树莓派程序层主导** 推进，原因如下：

1. `ControlProgram.on_tick(obs) -> list[Command]` 已经是当前系统中负责“读观测、做决策、发命令”的统一接口
2. ATP 状态机本质上是“根据当前观测和历史状态决定控制模式”的决策逻辑，天然属于树莓派控制程序层
3. 阶段 3 已经把底层真实性补到当前轮次所需水平，阶段 4 的主要矛盾不再是模型真实性，而是算法可比性
4. 如果在阶段 4 同时改底层模型和算法层，会让实验结果混入结构变化噪声，破坏 benchmark 公平性

本阶段默认结论：

1. ATP 状态机放在树莓派程序层实现
2. 算法基线作为独立 `ControlProgram` 或其派生组合实现
3. benchmark 和实验输出围绕树莓派程序层构建

## 3. 本阶段范围

### 3.1 要做的内容

1. **树莓派侧算法基线**
   - 保留现有 `BaselineTrackerProgram` 作为对照组
   - 新增跟踪控制基线
   - 新增预测器 + 控制器组合基线
   - 新增捕获 / 重捕获搜索策略基线

2. **ATP 状态机**
   - 在树莓派程序层增加最小 ATP 状态机
   - 至少覆盖 `SEARCH / ACQUIRE / TRACK_COARSE / TRACK_FINE / LOST / REACQUIRE`
   - 每个状态有明确输入、退出条件、输出命令行为

3. **统一 benchmark 流程**
   - 固定算法集合
   - 固定场景集合
   - 固定观测模式
   - 固定随机种子与结果目录结构
   - 一键运行并产出标准结果文件

4. **统一评测输出**
   - 结果格式遵循阶段 1 已冻结的实验输出规范
   - 补齐阶段 4 所需字段映射、命名和落盘位置
   - 形成可直接排序和汇总的结果表

5. **算法排序规则**
   - 固定每类场景内的排序方式
   - 固定总体优先级判据
   - 固定失败实验的处理方式

### 3.2 本阶段不做的内容

1. 不重做 `Target / Camera / Gimbal / Runtime` 的底层模型
2. 不新增新的物理真实性模型（如复杂背景、误警、多目标杂波、通信链路仿真）
3. 不重写阶段 3 已冻结的 `obs_filter` 三模式定义
4. 不修改现有命令总线和基础命令协议，除非出现**明确阻塞且无法在树莓派层规避**的最小缺口
5. 不追求首版算法最优，只追求“可比较、可复现、可扩展”

## 4. 默认决策（本阶段直接冻结）

为避免实施阶段再临时拍板，本计划直接固定以下默认决策：

1. ATP 状态机放在树莓派程序层
2. 阶段 4 默认不改底层模型
3. benchmark 主比较模式使用 `research`
4. `debug` 模式只用于故障定位和开发诊断，不进入正式排序表
5. `realistic` 模式作为扩展对照，不作为阶段 4 首轮主排序模式
6. 先做”可比较的基线集合”，不追求首版最强算法
7. 阶段 4 首轮至少形成：
   - 1 个对照算法（baseline_rate_p）
   - 2 个新增跟踪/预测类算法（rate_pi, alpha_beta_tracker/linear_kf_tracker）
   - 1 个带 ATP 状态机的搜索-跟踪组合基线
8. 架构采用”AtpControlProgram 持有 ATP 状态机 + 可插拔 tracker/predictor 组合”
9. 角度模式算法（angle_mode_tracker）仅参与 realistic 模式对照，不进入 research 主排序
10. EKF 算法移出首轮，标记为后续阶段候选

## 5. 任务拆分

### 任务 A：梳理树莓派算法框架

**目标**：把阶段 4 需要用到的控制程序组织方式先固定，避免后续每加一个算法就重复拼接结构。

**架构决策**：

采用”一个 AtpControlProgram 持有 ATP 状态机 + 可插拔 tracker/predictor 组合”的架构：

```
ControlProgram (现有协议)
  └─ AtpControlProgram (新增，实现 ControlProgram)
       ├─ AtpStateMachine (状态机：SEARCH/ACQUIRE/.../REACQUIRE)
       ├─ Tracker (可插拔策略协议)
       │    ├─ RatePTracker     (baseline_rate_p)
       │    ├─ RatePITracker    (rate_pi)
       │    └─ AngleModeTracker (angle_mode_tracker)
       └─ Predictor (可选，可插拔策略协议)
            ├─ None              (无预测，对应 baseline_rate_p 对照组)
            ├─ AlphaBetaFilter   (alpha_beta_tracker)
            └─ LinearKF          (linear_kf_tracker)
```

**内部接口定义**：

1. `Tracker` 协议：
   - `compute_commands(obs, atp_state, prediction) -> list[Command]`
   - 接收当前观测、ATP 状态和预测结果（可选），输出命令列表
2. `Predictor` 协议：
   - `update(obs, detection) -> None`
   - `predict(n_steps) -> predicted_pixel_position`
   - 接收观测和检测结果，输出预测像素位置
3. `AtpStateMachine`：
   - `update(detection_found, pixel_error) -> AtpState`
   - 纯状态转换逻辑，不直接发命令

**内容**：

1. 明确阶段 4 的算法组织方式：
   - 保留简单单文件控制器能力（现有 BaselineTrackerProgram 不改）
   - 新增 `AtpControlProgram` 作为统一入口，持有状态机和可插拔策略
2. 统一算法命名与版本命名方式：
   - `algorithm_name`
   - `algorithm_version`
3. 统一公共输入输出抽象：
   - 检测结果（复用 `detect_beacon_centroid` 返回的 `Detection`）
   - 丢失目标判据（通过 `Detection.found` 判定）
   - 命令构造方式（通过 `Command` dataclass）
4. 约束各算法都通过现有 `ControlProgram` 接口接入

**涉及模块**：

1. `entities/raspi/control_program.py`（不改动，保留现有协议）
2. `entities/raspi/tracker_program.py`（不改动，作为 baseline_rate_p 对照）
3. 新增 `entities/raspi/atp_state_machine.py`（ATP 状态机）
4. 新增 `entities/raspi/atp_control_program.py`（统一入口）
5. 新增 `entities/raspi/trackers/`（跟踪策略实现目录）
6. 新增 `entities/raspi/predictors/`（预测策略实现目录）

### 任务 B：建立跟踪算法基线

**目标**：形成至少一组能直接比较的跟踪控制基线。

**首轮固定算法集合**：

1. `baseline_rate_p`
   - 当前 `BaselineTrackerProgram` 的标准化对照版本
   - research 模式兼容：从 frame.image 做质心检测 → 像素误差 → 速率命令
2. `rate_pi`
   - 在速率模式下加入积分项
   - research 模式兼容：同 baseline_rate_p 输入链路
3. `angle_mode_tracker`
   - 使用云台角度模式（ANGLE_MODE），由控制器输出角度目标
   - **research 模式不可用**：角度模式需要知道云台当前角度（yaw_deg, pitch_deg），但 research 白名单不包含这些字段
   - 仅在 realistic 模式下运行（realistic 白名单包含 yaw_deg_internal, pitch_deg）

**算法-模式兼容性矩阵**：

| 算法 | debug | research | realistic |
|------|-------|----------|-----------|
| `baseline_rate_p` | ✅ | ✅ | ✅ |
| `rate_pi` | ✅ | ✅ | ✅ |
| `angle_mode_tracker` | ✅ | ❌ | ✅ |

> **research 模式约束**：research 白名单仅保留 `timestamp / gimbal.mode / camera.f_current_mm / frame`。控制器只能通过帧图像检测结果（`detect_beacon_centroid` 返回值）判断目标是否存在，不能依赖 `camera.in_fov`（被屏蔽）。角度模式算法需要 gimbal 角度反馈，在 research 模式下不可运行。

**统一要求**：

1. 都只使用当前 `obs_mode` 允许的字段
2. 都支持失去目标时的统一降级策略
3. 都能输出同一组实验结果字段

### 任务 C：建立预测算法基线

**目标**：把”无预测 vs 轻量预测”纳入统一比较。

> **说明**：任务 B 的 `baseline_rate_p` 已经覆盖了”无预测 + 速率 P 控制”这一档。任务 C 专注于”在相同跟踪器基础上加入预测器”的增量对比。首轮 benchmark 中，`baseline_rate_p` 同时充当”无预测”对照组。

**首轮固定算法集合**：

1. `alpha_beta_tracker`
   - 基于 `baseline_rate_p` 跟踪器 + alpha-beta 预测器
   - 预测器输入：帧检测像素序列；输出：预测像素位置 → 替代当前像素误差送入控制器
   - research 模式兼容
2. `linear_kf_tracker`
   - 基于 `baseline_rate_p` 跟踪器 + 线性卡尔曼滤波器（状态=[像素位置, 像素速度]）
   - 预测器输入：帧检测像素序列；输出：预测像素位置
   - research 模式兼容

**移出首轮的算法**：

- `extended_kf_tracker`（EKF）：需要加速度观测或角度反馈，research 模式下输入不足，实现复杂度显著高于其他基线。标记为后续阶段候选。

**固定边界**：

1. 预测器只能使用观测模式允许的输入
2. 不允许读取 target 真值做预测
3. 预测输出必须清晰映射到控制器输入，不允许隐含耦合
4. 预测器内部状态只允许使用历史观测序列推算，不允许注入外部信息
5. 预测器算法与 `baseline_rate_p` 的唯一区别是像素误差来源（实际检测 vs 预测位置），控制增益等参数保持一致

### 任务 D：建立 ATP 状态机

**目标**：把捕获、跟踪、失锁、重捕获流程在树莓派程序层打通。

**固定状态列表**：

1. `SEARCH`
   - 执行预定义搜索路径，等待目标进入可检测状态
2. `ACQUIRE`
   - 首次发现目标后的短时确认状态，避免单帧误检或偶发亮点抖动直接进入跟踪
3. `TRACK_COARSE`
   - 目标已进入视场，但误差仍较大时的粗跟踪
4. `TRACK_FINE`
   - 误差持续稳定在阈值内时的精跟踪
5. `LOST`
   - 连续 N 帧丢失目标后的失锁状态
6. `REACQUIRE`
   - 按限定搜索策略尝试重新捕获目标

**固定状态切换条件**：

1. `SEARCH -> ACQUIRE`
   - 连续 `n_detect_enter` 帧检测到目标
2. `ACQUIRE -> TRACK_COARSE`
   - 目标连续 `n_acquire_confirm` 帧检出，且像素误差有限
3. `TRACK_COARSE -> TRACK_FINE`
   - 误差连续 `n_fine_enter` 帧低于粗/精切换阈值
4. `TRACK_FINE -> LOST`
   - 连续 `n_lost_enter` 帧未检出目标
5. `TRACK_COARSE -> LOST`
   - 连续 `n_lost_enter` 帧未检出目标
6. `LOST -> REACQUIRE`
   - 失锁后立即进入重捕获流程
7. `REACQUIRE -> ACQUIRE`
   - 连续 `n_detect_enter` 帧重新检出目标
8. `REACQUIRE -> SEARCH`
   - 重捕获超时或完整扫描失败

**ATP 状态机配置参数（纳入 config.py 新增 ATPStateMachineConfig）**：

| 参数 | 类型 | 默认值 | 含义 |
|------|------|--------|------|
| `n_detect_enter` | int | `3` | 进入 ACQUIRE 所需连续检出帧数 |
| `n_acquire_confirm` | int | `5` | ACQUIRE → TRACK_COARSE 所需连续检出帧数 |
| `n_lost_enter` | int | `5` | 进入 LOST 所需连续丢失帧数 |
| `n_fine_enter` | int | `10` | 粗跟踪→精跟踪所需连续低误差帧数 |
| `coarse_error_threshold_px` | float | `50.0` | 粗/精切换像素误差阈值 |
| `search_yaw_range_deg` | float | `180.0` | 搜索方位角范围（对称） |
| `search_pitch_range_deg` | float | `90.0` | 搜索俯仰角范围（对称） |
| `search_step_deg` | float | `5.0` | 搜索步进角度 |
| `search_dwell_frames` | int | `3` | 每步停留帧数 |
| `search_rate_dps` | float | `30.0` | SEARCH 开环/闭环扫描的名义角速度 |
| `reacquire_timeout_s` | float | `5.0` | 重捕获超时秒数 |
| `reacquire_search_step_deg` | float | `10.0` | 重捕获搜索步进（比首次搜索粗） |
| `reacquire_search_rate_dps` | float | `45.0` | REACQUIRE 阶段的名义搜索角速度 |

**固定搜索策略首版**：

1. 首版采用**确定性光栅扫描路径**（水平优先，逐行递进）
2. 不引入随机搜索
3. 搜索从 (yaw=0, pitch=0) 开始，先水平后垂直
4. 重捕获时使用更粗的步进（`reacquire_search_step_deg`）和小范围扫描

**research 模式下的搜索策略**：

research 白名单不包含 gimbal 角度反馈，SEARCH 状态无法做闭环角度定位。因此：

1. research 模式下 SEARCH 采用**开环定时扫描**：按 `search_rate_dps` 发送 yaw/pitch 速率命令，按 `search_dwell_frames` 控制每步持续时间
2. 不依赖角度反馈确定扫描进度，而是通过 `search_step_deg / search_rate_dps / tick_dt` 计算每步持续 tick 数；若与 `search_dwell_frames` 冲突，以显式配置的 `search_dwell_frames` 为准
3. realistic 模式下 SEARCH 可以做**闭环扫描**：读取 gimbal 角度反馈精确控制扫描路径，但仍复用相同的 `search_rate_dps` / `search_step_deg` / 搜索范围配置
4. REACQUIRE 阶段采用更快的 `reacquire_search_rate_dps` 和更粗的 `reacquire_search_step_deg`
5. 两种模式的搜索覆盖范围相同，只是定位精度不同

**ACQUIRE 阶段“像素误差有限”的定义**：

1. 检测结果必须满足 `Detection.found=True`
2. `cx / cy` 必须非空且为有限数值（非 NaN、非 inf）
3. 仅在满足以上条件时，才计入 `n_acquire_confirm` 连续确认计数

**固定失锁判据首版**：

1. 以”连续未检出帧数”为主判据
2. 不把控制误差过大单独视为失锁
3. 丢检、亮度变化和近真实噪声统一通过检测失败体现

### 任务 E：建立统一 benchmark 流程

**目标**：让不同算法在同一条件下可重复比较。

**固定 benchmark 维度**：

1. **场景维度**（直接引用阶段 1 冻结编号）
   - 首轮使用标准组合 B1、B2、B3（见阶段 1 场景矩阵文档 §8）
   - B1 = S2-D2-V2-W2-M2-O0-L0-P1（当前基线对照，对应 sinusoidal x=100m）
   - B2 = S2-D2-V2-W2-M2-O0-L1-P1（轻非理想验证，延时 L1）
   - B3 = S3-D3-V3-W3-M2-O0-L2-P2（中难度比较）
2. **观测模式**
   - 正式主比较：`research`
   - 扩展对照：`realistic`（用于 angle_mode_tracker 等需要 gimbal 反馈的算法）
3. **延时定义说明**
   - 首轮正式 benchmark 直接使用 B1 / B2 / B3 作为完整工况组合
   - 不再把延时档位单独展开成交叉维度，避免与 B 组合内已冻结的 `L0 / L1 / L2` 重复定义
   - 如需单独做延时消融，后续可在阶段 4 扩展实验中使用 `scenario_id + Lx` 的正交设计，但不属于首轮验收集
4. **随机种子**
   - 固定种子列表：`[42, 123, 456, 789, 1024]`
5. **算法集合**
   - 每次 benchmark 输入明确算法名单，不允许隐式扫描全部模块

**固定 benchmark 输出**（严格遵循阶段 1 实验输出规范）：

1. 目录结构：`output/experiments/<scenario_id>/<condition_id>/<algorithm_name>/<experiment_id>/`
2. 必须生成文件：
   - `result.json`（最小 JSON 结构见阶段 1 实验输出规范 §5）
   - `metrics.csv`（字段见阶段 1 实验输出规范 §6）
   - `notes.md`
   - `error_curve.png`
   - `state_timeline.png`
3. `scenario_id` / `condition_id` 使用阶段 1 冻结编号（如 `S2` / `B1`）
4. `observation_mode` / `algorithm_name` / `algorithm_version` / `seed` 必填
5. 当前无法自动计算的 ATP 指标（A1/A2/A5/A6）允许留空，但字段必须保留

### 任务 F：形成排序与验收规则

**目标**：避免“跑出很多结果但没有统一结论”。

**固定排序原则**：

1. 先按场景组内排序
2. 再看跨场景总体稳定性
3. 最差场景表现权重高于最好场景表现
4. 失败实验不得直接忽略，必须计入结果表

**固定失败处理规则**：

1. 实验崩溃：写入 `failure_reason`
2. 未捕获成功：`capture_success_rate=0`
3. 多次失锁：如实记录 `lock_loss_rate`
4. 无法重捕获：`reacquire_time_s` 留空并记录失败原因

## 7. 风险点与控制方式

### 风险 1：树莓派程序层承载过多职责，导致实现臃肿

**控制**：

1. 将阶段 4 内部结构拆为“状态机 / 预测器 / 控制器 / benchmark”四层
2. 每层职责单一，不把所有逻辑堆进一个 `on_tick()`

### 风险 2：现有控制程序接口不足以支持 benchmark

**控制**：

1. benchmark 结果采集默认基于现有 `WorldSnapshot`
2. 若缺字段，优先在工具层计算，不先动底层实体
3. 只有满足“最小补接口触发条件”时才补接口

### 风险 3：不改底层模型会限制某些算法

**控制**：

1. 阶段 4 首轮只纳入能在现有阶段 3 平台上公平比较的算法
2. 对明确依赖更复杂感知模型的算法，标记为后续阶段候选，不在本阶段强行落地

### 风险 4：不同观测模式下算法不可比

**控制**：

1. 正式主排序统一只在 `research` 模式下进行
2. `realistic` 模式只作为扩展退化对照
3. `debug` 模式不得进入正式比较表

### 风险 5：ATP 状态机切换条件写得模糊，后续结果不可复现

**控制**：

1. 所有状态进入/退出阈值写入配置
2. 所有判据以“连续帧数 / 误差阈值 / 超时阈值”明确定义
3. 测试中固定种子和场景，验证切换可复现

### 风险 6：不同算法在不同 obs_mode 下可比性不足

**控制**：

1. research 模式主排序只纳入可在 research 下运行的算法（速率模式）
2. 角度模式算法只在 realistic 对照组中比较
3. 算法-模式兼容性矩阵在任务 B 中提前固定
4. 不允许为了某个算法特殊需求放宽 research 白名单

### 风险 7：结果输出不统一，后续阶段无法自动汇总

**控制**：

1. 结果 schema 直接复用阶段 1 实验输出规范
2. `algorithm_name / algorithm_version / observation_mode / scenario_id / condition_id / seed` 必填
3. benchmark 工具直接输出 JSON + CSV 两种结果
