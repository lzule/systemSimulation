# GUI 重设计方案

> 目标：在现有 GUI 结构基础上做增量优化，把当前"工程调试型窗口"提升为"科研操作型仪表盘"，让界面与当前能力匹配、观感更统一、操作更顺手。

> 约束：本次不做推翻式改造，不重写 runtime 生命周期，不引入大范围热重载，不把 benchmark/录制/回放/多算法并排对比强行塞进当前 GUI。

---

## 1. 设计目标

本次重设计的目标不是"换一个新皮肤"，而是让当前 GUI 更符合真实使用场景：

- 一眼看清系统现在在做什么
- 常用操作尽量不离开界面
- 研究、演示、调试三种场景都能顺手使用
- 保持学术风格，避免花哨和噪声
- 与当前 CLI、工具链、文档体系口径一致

---

## 2. 当前界面现状

当前 GUI 已经不是空壳，而是具备完整基础能力：

- 世界视图：目标轨迹、云台指向、FOV
- 双视角：原始相机视角 + Raspi 延时视角
- 时间轴：像素误差、角度误差、角速度
- 核心状态：仿真时间、控制模式、姿态、误差、backlog、obs_lag、ATP 状态、obs_mode、target_type
- 诊断区：目标 / 云台 / 相机 / Raspi 的细字段

因此，本次重点不是"补齐基础功能"，而是"重组信息层级"和"让操作路径更符合研究使用方式"。

### 2.1 当前布局示意

```text
+----------------------------------------------------------------------------------+
| 控制栏  [开始] [暂停] [重置] [保存快照]  延时输入[___]ms [应用]  FPS  状态        |
+------------------------------------------+---------------------------------------+
| 左侧 (约 60%)                            | 右侧 (约 40%)                         |
| +--------------------------------------+ | +-----------------------------------+ |
| | 世界视图                             | | | 双视角对比                        | |
| | 轨迹 / 云台指向 / FOV                | | | 原始相机 | Raspi 延时             | |
| +--------------------------------------+ | +-----------------------------------+ |
| +--------------------------------------+ | +-----------------------------------+ |
| | 时间轴                               | | | 信息区                           | |
| | 像素误差 / 角速度 / 角度误差         | | | [核心状态] [诊断信息]            | |
| +--------------------------------------+ | +-----------------------------------+ |
+------------------------------------------+---------------------------------------+
```

### 2.2 当前布局的优点

- 左右分栏逻辑基本合理：左侧看整体，右侧看局部和诊断
- 世界视图占比大，适合先看结果
- 双视角对比很直观，能直接看延时影响
- 诊断区已经具备实体级细字段，不需要重做

### 2.3 当前布局的主要问题

- 控制栏信息太挤，状态和动作混在一排里
- 核心状态还是"表格心智"，重点不够突出
- 关键状态虽然都在，但没有真正形成"第一眼摘要"
- 时间轴还缺 ATP 状态迁移这一类研究信息
- 保存功能偏弱，只是截图，没有运行摘要
- 当前方案必须兼容非 ATP 控制程序，但这一点容易在设计时被忽略

### 2.4 已知代码遗留

- `apply_target_overrides(cfg)` 在 GUI 路径下曾被调用了两次：`runner.py:25` 和 `window.py` 的 `__init__`。当前已去掉 `runner.py` 里的那次，保留 `window.py` 内的调用。

---

## 3. 必须遵守的边界

本次设计必须明确边界，避免方案脱离工程现实。

### 3.1 本次一定不做

- 不推翻当前左右分栏主结构
- 不新增左侧"实验配置面板"并要求 runtime 热重载
- 不在 GUI 内直接启动 benchmark
- 不在 GUI 内直接做 record / replay
- 不做多算法并排运行
- 不做 realtime / offline 热切换
- 不把快捷键当作本次硬交付项

### 3.2 原因说明

- 当前 `worker` 和 `runtime` 生命周期不是按热重载设计的
- benchmark / 录制 / 回放属于工具链能力，不是单窗口能力
- 多算法并排意味着多 runtime、多线程、多画面同步，复杂度明显越界
- `pyqtgraph` 图表区会拦截部分键盘事件，快捷键要做也只能作为后续增强

---

## 4. 设计原则

1. 先看结果，再看细节
2. 运行控制放前面，深度诊断放后面
3. 核心状态必须一眼可读，不能藏在表格里
4. 视觉要克制，强调数据，不抢数据
5. 保留现有功能，不做为了好看而削弱能力的改造
6. 增量改造，不推翻现有结构
7. 所有新增显示都必须兼容 ATP 与非 ATP 两类控制程序

---

## 5. 目标使用场景

### 5.1 日常观察

重点是：

- 目标是否在视野内
- ATP 是否处于合适状态
- 误差是否收敛
- 延时是否异常

### 5.2 算法研究

重点是：

- 当前控制程序
- 当前目标运动类型
- 当前观测模式
- 时间轴上的误差变化
- ATP 状态随时间的变化

### 5.3 问题排查

重点是：

- Raspi 延时链路
- 状态迁移过程
- 云台 / 相机 / 目标 / Raspi 的细字段
- 关键事件与截图导出

## 6. 目标界面结构

### 6.1 总体策略

保留现有"左侧主观察 + 右侧局部观察和诊断"的主结构，只在各区域内部重组，不新增第三列，不重写主布局逻辑。

### 6.2 目标布局示意

```text
+----------------------------------------------------------------------------------+

+------------------------------------------+---------------------------------------+
| 左侧主观察区 (约 60%)                    | 右侧分析区 (约 40%)                   |
| +--------------------------------------+ | +-----------------------------------+ |
| | 世界视图                             | | | 双视角对比                        | |
| | 轨迹 / 云台 / FOV / 标题摘要         | | | 原始相机 | Raspi 延时             | |
| +--------------------------------------+ | +-----------------------------------+ |
| +--------------------------------------+ | +-----------------------------------+ |
| | 时间轴                               | | | 状态卡片区                        | |
| | 像素误差 / 角度误差 / 角速度         | | | 误差 / 姿态 / in_fov / backlog    | |
| | ATP 状态带                           | | +-----------------------------------+ |
| +--------------------------------------+ | +-----------------------------------+ |
|                                          | | 诊断区                              | |
|                                          | | [目标][云台][相机][Raspi]          | |
|                                          | | 字段表格                            | |
|                                          | +-----------------------------------+ |

```

### 6.3 右侧面板空间分配

当前右侧 stretch 比例为双视角 6 : 信息区 4。状态卡片插入后建议调整为：

| 区域 | 当前 stretch | 目标 stretch | 说明 |
|------|-------------|-------------|------|
| 双视角 | 6 | 5 | 略微压缩 |
| 状态卡片 | — | 2 | 新增，替代原核心状态 Tab |
| 诊断区 | 4 | 3 | 略微压缩 |

总计保持 10 份，不改变右侧总占比（40%）。

### 6.4 当前布局与目标布局对照

```text
当前：控制栏一排塞满 -> 世界视图/时间轴在左 -> 双视角/Tab 在右
目标：状态摘要一排 + 操作一排 -> 左侧仍是世界视图/时间轴 -> 右侧变成"双视角 + 状态卡 + 诊断"
```

## 7. 各区域设计

### 7.1 顶部摘要条

将当前单行控制栏拆为两层：

- 第一层：状态摘要
- 第二层：操作按钮

建议第一层显示：

- 运行状态
- 当前时间
- ATP 状态（非 ATP 控制程序时显示 `--`）
- 当前控制程序
- obs_mode
- target_type
- 当前延时
- backlog

这样做的目的，是把"系统现在是什么状态"从按钮堆里拆出来。

### 7.2 左侧主观察区

保持现有结构不变：

- 上：世界视图
- 下：时间轴

只做两类增强：

- 世界视图标题摘要增强
- 时间轴增加 ATP 状态带

#### 时间轴增强示意

```text
+----------------------------------------------------------+
| 像素误差 / 角度误差                                      |
|  ────────╮     ╭────────────╮                            |
|          ╰─────╯            ╰────                        |
+----------------------------------------------------------+
| 角速度                                                   |
|  ──╮   ╭────╮     ╭────╮                                  |
|    ╰───╯    ╰─────╯    ╰────                              |
+----------------------------------------------------------+
| ATP 状态带                                               |
| SEARCH | ACQUIRE | TRACK_COARSE | TRACK_FINE | LOST ...  |
+----------------------------------------------------------+
```

**数据依赖**：当前 `state_buffer.py` 只存储 `t_hist/x_hist/y_hist/rate_hist/angle_err_hist/err_hist`，不包含 `atp_state` 历史。实现 ATP 状态带需要先在 `state_buffer.py` 的 `push()` 方法中追加 `self.atp_state_hist` 的存储，并在 `read_curves()` 中返回。这是一项前置改动，难度低但必须明确。

### 7.3 右侧分析区

右侧分成三层：

- 双视角
- 状态卡片（替代原核心状态 Tab）
- 诊断区

#### 状态卡片示意

```text
+----------------+----------------+
| 像素误差       | 角度误差       |
| 12.3 px        | 5.2 deg        |
+----------------+----------------+
| yaw / pitch    | u / v          |
| 5.2 / 0.0      | 322 / 241      |
+----------------+----------------+
| in_fov         | backlog        |
| YES            | 1              |
+----------------+----------------+
```

这些卡片不是替代诊断表，而是替代原来的核心状态纯表格，让一眼可读。

**布局实现**：状态卡片直接替换原 `info_tabs` 中的"核心状态"Tab。具体做法是将 `tab_core` 的内容从 GridLayout 标签改为卡片网格，不再需要 Tab 切换——诊断区直接平铺在卡片下方。

### 7.4 底部抽屉

本次建议先只定义结构，不强制一步做满。

可收纳内容：

- 事件日志
- 导出摘要

默认收起，避免压缩主视图。

> **注意**：原方案提到"运行备注"，但 GUI 中没有文本输入控件，备注无处输入。本次不纳入"运行备注"功能。如果后续需要，需要先新增文本输入控件。

## 8. 信息分层

### 8.1 一级信息

必须第一眼可见：

- ATP 状态
- 是否在视野内
- 误差大小
- 延时大小
- backlog
- 当前控制程序
- 当前 obs_mode
- 当前 target_type

### 8.2 二级信息

放在状态卡片或摘要区：

- yaw / pitch
- u / v
- du / dv
- yaw_rate / pitch_rate
- 角度误差

### 8.3 三级信息

保留在诊断表内：

- delay_metrics
- command_apply_ts
- raw_frame_ts / raspi_frame_ts
- x / y / z / vx / vy / vz
- 其他实体内部字段

## 9. 视觉方案

### 9.1 风格方向

保留当前"学术仪表盘"方向，不另起一套视觉语言：

- 浅冷灰背景
- 白色面板
- 深蓝灰文字
- 关键状态用少量高对比色

### 9.2 配色原则

沿用当前 `COLOR` 字典：

- 背景：`#f6f7fb`
- 面板：`#ffffff`
- 主文字：`#1f2a44`
- 正常：绿色
- 过渡：橙色
- 异常：红色
- 主观察色：蓝色系

### 9.3 组件风格

- 状态卡片：圆角、轻边框、数字加粗
- ATP 状态：颜色 + 文本双重表达
- 图表：背景干净，网格轻量
- 诊断区：继续用表格，但不要升到视觉中心

### 9.4 尺寸适配

本次按桌面研究环境设计：

- 推荐尺寸：`1680 x 980`
- 最低保证：`1360 x 860`

小尺寸下建议退化策略：

- 保留世界视图和状态卡
- 压缩诊断区高度
- 底部抽屉默认收起

## 10. 功能范围

### 10.1 本次纳入

- 顶部状态摘要条
- 顶部操作条分层
- 核心状态卡片化（替换原核心状态 Tab）
- ATP 状态带（含 `state_buffer.py` 前置改动）
- 截图导出增强（截图 + summary.json）
- 清理 `apply_target_overrides` 重复调用
- 文档口径同步

### 10.2 本次不纳入

- GUI 内 benchmark
- GUI 内 record / replay
- 多算法并排运行
- 运行内切换控制程序
- 运行内切换 target_type / obs_mode
- 配置模板热加载
- 强制全局快捷键
- 运行备注（缺少输入控件）

### 10.3 不纳入原因

这些能力都要求当前 GUI 之外的生命周期改造，不适合混进这轮界面升级。

## 11. 交互设计

### 11.1 保持不变的主流程

1. 通过 CLI 启动并带入参数
2. 进入 GUI
3. 开始 / 暂停 / 重置
4. 观察世界视图、双视角和时间轴
5. 需要时打开诊断区
6. 截图或导出摘要

### 11.2 截图与导出

本次"导出"建议定义为轻量导出：

```text
output/ui_exports/<timestamp>/
├── dashboard.png
└── summary.json
```

导出内容：

- `dashboard.png`：当前窗口截图
- `summary.json`：控制程序、obs_mode、target_type、delay、ATP 状态、误差摘要

> **注意**：原方案包含 `note.txt`，但 GUI 中没有文本输入控件来写备注，本次不纳入。

### 11.3 快捷键说明

快捷键仅保留为可选增强项：

- 空格：开始 / 暂停
- R：重置
- S：保存截图

但本次不作为硬要求，因为 `pyqtgraph` 会拦截部分键盘事件。

## 13. 兼容性要求

这次方案必须同时兼容两类控制程序：

### 13.1 ATP 控制程序

- 正常显示 ATP 状态
- 正常显示 ATP 状态带

### 13.2 非 ATP 控制程序

- ATP 区域显示 `--`
- ATP 状态带显示为空白或灰色横条
- 界面不能报错
- 状态卡和诊断区布局不能错位

这是本次方案里必须明确写死的要求，避免界面只适配 ATP 路径。

## 14. 风险评估

| 风险 | 等级 | 应对 |
|------|------|------|
| 改控制栏后影响现有操作习惯 | 低 | 保留原按钮行为，只重排层级 |
| 卡片化导致信息密度下降 | 低 | 诊断区不动，卡片只承接一级信息 |
| ATP 状态带引入额外绘图复杂度 | 中 | 仅做轻量状态带，不重做整个时间轴 |
| `state_buffer` 改动影响时间轴数据 | 低 | 只追加字段，不改现有字段 |
| 右侧三层挤压诊断区可见性 | 中 | 调整 stretch 比例为 5:2:3 |
| 小尺寸窗口布局拥挤 | 中 | 先保证推荐尺寸，给出退化策略 |
| 快捷键与图表冲突 | 中 | 不纳入本次硬交付 |

## 15. 开发拆分

### 15.1 第一步：顶部摘要条与操作条分层

- 改控制栏排布
- 保留原按钮和延时调节逻辑
- 顺手清理 `runner.py` 中重复的 `apply_target_overrides`

**验收**：启动 GUI，确认控制栏分两层显示，按钮功能不变

### 15.2 第二步：核心状态卡片化

- 用卡片替换原核心状态 Tab 的视觉表达
- 数据来源不变（`_update_core_tab`）
- 移除 Tab 切换，诊断区平铺在卡片下方

**验收**：启动 GUI，确认右侧显示卡片 + 诊断区，数据实时刷新

### 15.3 第三步：时间轴增加 ATP 状态带

- **前置改动**：`state_buffer.py` 的 `push()` 追加 `self.atp_state_hist`
- **前置改动**：`state_buffer.py` 的 `read_curves()` 返回 ATP 状态历史
- 在时间轴下方加轻量彩色状态带
- 非 ATP 控制程序下状态带显示灰色

**验收**：使用 AtpControlProgram 启动 GUI，确认状态带颜色随状态变迁；使用 BaselineTrackerProgram 确认不报错

### 15.4 第四步：截图导出增强

- 增加运行摘要导出（`summary.json`）
- 保留原截图能力

**验收**：点击导出，确认 `output/ui_exports/` 下生成 `dashboard.png` + `summary.json`

## 17. 结论

这次 GUI 重设计的核心，不是做一个全新的大而全界面，而是在当前结构内把"状态、观察、诊断、导出"重新摆对位置。
只要守住增量改造边界，这次升级就能既贴合当前项目能力，又明显提升实际可用性。
