# 低空场景无线光通信 ATP 开发文档

## 1. 文档目的

本文档用于指导当前仿真系统后续开发，目标不是立刻做完整样机，而是先把系统建设成一个**面向低空场景无线光通信捕获、跟踪、瞄准的研究与算法筛选平台**。

本文档强调三点：

1. **开发顺序必须严格**，不能跳阶段推进。
2. **每阶段必须有明确产出**，不能只停留在“有思路”。
3. **每阶段必须可验收**，不能只看主观感觉。

---

## 1.1 当前系统技术现状（阶段 3 完成后复核）

> 以下结论基于阶段 3 完成后的源码与测试复核（2026-05-16），作为进入阶段 4 的当前基线。

| 维度 | 现状 | 依据 |
|------|------|------|
| 目标模型 | **3D**（x, y, z + vx, vy, vz） | `TargetKinematics3D` 已输出 z、俯仰角和 3D 距离 |
| 视觉闭环 | **双轴**（yaw + pitch） | 相机双轴投影 + 跟踪程序双轴速率控制已打通 |
| 云台控制器 | **已支持双轴**角度模式和速率模式 | `CascadedController2Axis` 对 yaw/pitch 独立计算外环 P + 内环 PI |
| 成像模型 | **近真实针孔成像** | 支持距离相关 sigma、亮度衰减/抖动、偶发丢检 |
| 检测算法 | **阈值 + 质心**（threshold=180） | `detect_beacon_centroid` 只做阈值分割 + 均值 |
| 延时模型 | **latest/fifo 双策略** | 默认 latest；新增有限队列 fifo 和多速率控制采样 |
| 坐标系 | **无统一定义**，隐式约定 | bearing = atan2(y, x)，gimbal 在原点 |
| ATP 概念 | **代码中无任何 ATP 概念** | 无捕获/粗跟踪/精跟踪/瞄准状态机 |
| 观测模式 | **已分层** | debug / research / realistic 三模式已实现，研究/近真实模式禁止直接读取 target 真值 |
| 测试覆盖 | **阶段 3 回归已补齐** | 阶段 3 新增成像、观测过滤、云台非理想、延时策略回归测试并通过 |

## 2. 项目目标

### 2.1 总目标

围绕低空场景无线光通信任务，建立一套可持续迭代的 ATP 平台，用于研究和筛选：

- 捕获方法
- 跟踪方法
- 瞄准方法
- 失锁恢复方法
- 延时补偿方法
- 后续与通信链路联合优化的方法

### 2.2 研究对象

目标对象包括：

- 地面站
- 低空飞行器
- 地面小车
- 一般移动物体

### 2.3 当前阶段定位

当前优先级不是硬件落地，而是：

- 先把仿真平台做对
- 先把问题定义清楚
- 先把算法比较框架搭起来
- 先筛出值得投入的技术路线

---

## 3. 当前基础与已知边界

基于全量源码审阅（§1.1），当前系统具备以下基础：

- 已有 Target、Gimbal、Camera、Raspi 四实体闭环
- 已有统一 tick 调度（dt=5ms，200Hz）
- 云台控制器**已支持双轴**角度/速率模式（串级 PID：外环 P 50Hz + 内环 PI 200Hz）
- 已有基础视觉跟踪控制程序（BaselineTrackerProgram，P 控制器）
- 已有无 GUI 和 GUI 运行方式
- 已有较完整的单体测试和模块测试（224+8）
- 参数已集中到 config.py（11 个 dataclass）
- 延时管线已支持 latest/fifo 两种缓冲策略

当前系统的明确边界：

- 虽已具备 3D 目标、双轴闭环和近真实成像，但仍未进入 ATP 状态机层
- 图像模型仍属于受控简化模型（单目标、无杂波、无复杂背景、无误警）
- 无 ATP 概念（无捕获/粗跟踪/精跟踪/失锁恢复状态机）
- 已实现观测模式分层，但 realistic 模式仍是“受限观测仿真”，不是完整真实载荷
- 已有基线端到端闭环测试与阶段 3 回归测试，但算法评价体系仍待阶段 4 完善
- 还不是 ATP+通信联合平台

因此，后续开发不能直接从”算法花样”开始，而必须先做平台收口和能力升级。

## 4. 开发原则

### 4.1 顺序原则

必须按下面顺序推进：

1. 基线收口
2. 问题定义冻结
3. 双轴几何升级
4. 近真实建模
5. 算法基线建设
6. 平台固化与研究输出

### 4.2 验收原则

每阶段结束时必须同时满足：

- 代码可运行
- 文档已补齐
- 测试已补齐
- 输出结果可复现

### 4.3 约束原则

本阶段默认约束如下：

- 不引入新的大型框架重写现有系统
- 保持 Python 平台为主
- 先聚焦 ATP，通信链路在本开发文档中只保留对接位置，不作为本轮主开发项
- 所有新增关键参数必须进入统一配置，禁止继续扩散硬编码

## 阶段 2：双轴 ATP 升级 `🟢 已完成`

> 实施前详细计划文档：`docs/阶段2-双轴ATP升级/阶段2详细开发计划.md`

### 目标

把当前”一轴亮点跟踪原型”升级成真正可研究双轴 ATP 的几何与控制底座。

### 任务

1. **统一坐标系定义（优先完成，一切后续改动的基础）**：
   - 定义世界坐标系（ENU 或 NED，明确原点、轴向、角度正方向）
   - 定义云台姿态（yaw/pitch 正方向、零位）
   - 定义光轴方向与视线角（azimuth + elevation）
   - 定义目标位置→视线角的映射关系
   - 写入独立文档，所有代码以此为基准

2. **将目标模型从 2D 升级到 3D**：
   - 增加 z 位置和 vz 速度
   - bearing 改为 azimuth（方位角），新增 elevation（俯仰角）
   - distance 改为 3D 距离（sqrt(x²+y²+z²)）
   - 支持低空飞行轨迹（含高度变化的航点）
   - 注意：这将**破坏所有现有测试**中的 bearing/distance 断言

3. **重构相机投影模型**：
   - 同时计算 u 和 v（v 不再硬编码为 h/2.0）
   - 引入 elevation 角参与 v 坐标计算
   - 当前 bearing 计算使用 `atan2(y, x)`（2D 方位角），升级后需同时计算 elevation 角
   - alpha 的含义从”方位偏差”变为包含方位+俯仰的双角偏差
   - 支持双轴视线误差

4. **启用双轴控制闭环**：
   - 云台控制器已支持双轴（无需改动 CascadedController2Axis）
   - 重构 BaselineTrackerProgram：同时输出 yaw_rate 和 pitch_rate
   - TrackerTuning 增加 pitch 相关参数（pitch_rate_kp、max_pitch_rate 等）
   - 不再固定 pitch_rate 为 0

5. **补双轴几何测试和行为测试**：
   - 3D 目标位置 → 双角视线角 → 双像素坐标的几何正确性测试
   - 双轴闭环基线测试（稳态双轴误差）
   - 更新全部被 2D→3D 破坏的旧测试

### 阶段产出

- 双轴 ATP 几何底座
- 3D 目标模型
- 双轴相机投影模型
- 双轴闭环基线演示

### 完成标准

- 系统不再被称为一轴系统
- 双轴误差可以被正确观测与控制
- 双轴几何测试全部通过

### 阶段闸门

进入阶段 3 之前，必须同时满足：

- [x] 坐标系定义文档已完成并冻结
- [x] 3D 目标状态、双轴投影、双轴控制三部分已经全部打通
- [x] 双轴几何测试覆盖上下左右前后六类基本方位
- [x] 旧测试已完成清理，不再残留 2D 假设导致的错误通过

### 阶段风险

- **这是当前系统最大的结构升级点，改动面覆盖 4 个实体 + 全部测试**
- 坐标系定义必须先于代码改动完成，否则所有角度计算会出错
- 2D→3D 升级会**破坏所有现有测试**中的 bearing/distance 断言，需要逐个修复
- 如果坐标系定义不统一，后续所有算法都容易出错
- 预计影响文件：target/model.py、target/entity.py、camera/model.py、camera/entity.py、raspi/tracker_program.py、config.py、全部 224 个单元测试 + 8 个集成测试

## 阶段 3：近真实建模 `🟢 已完成`

### 目标

让平台具备研究算法鲁棒性的能力，而不是只在理想条件下有效。

> **注意**：本阶段内容较多，建议分两轮交付：
> - **轮 A**：感知真实性（成像 + 检测 + 丢检）— 优先级最高，直接影响跟踪算法的可信度
> - **轮 B**：执行器真实性（云台非理想 + 延时策略）+ 控制器输入模式分离

### 任务

#### 轮 A：感知真实性（优先）

1. **扩展目标成像模型**：
   - 目标大小随距离变化（sigma = f(distance)，取代固定 σ=3.2）
   - 亮度随机变化（模拟大气衰减和目标反射率变化）
   - 偶发丢检（in_fov 但检测失败的概率模型）
   - 这三项是**让跟踪算法研究有价值的最小改动**

2. **实现控制器输入模式分离**（obs_filter 层）：
   - `debug` 模式：透传全部 obs（含 target/gimbal 真值）
   - `research` 模式：只保留 frame + gimbal.mode + camera.f_current_mm
   - `realistic` 模式：frame + 有噪声的 gimbal 状态 + 无 target
   - 三种模式通过 config 或 CLI 参数切换

3. **为轮 A 补回归测试**。

#### 轮 B：执行器真实性

4. **扩展云台非理想项**：
   - 编码器量化噪声（位置读出加噪声）
   - 静摩擦/死区（低速率命令被吸收）
   - 参数偏差（实际 τ 偏离标称值 ±20%）
   - 这些让"鲁棒控制"成为可研究的问题

5. **扩展延时模型选项**：
   - 保留单槽抓最新帧作为默认
   - 增加有限队列模式（1-3 帧缓冲）
   - 增加多速率采样与控制选项
   - 三种策略通过 config 切换

6. **杂波与干扰（可选，按需开启）**：
   - 随机假目标（非目标亮点）
   - 背景噪声增强
   - 多目标干扰

7. **将新增研究参数全部纳入统一配置**。
8. **为轮 B 补回归测试**。

### 阶段产出

- 轮 A：近真实感知模式 + obs_filter 三种模式 + 丢检模拟 + 回归测试
- 轮 B：近真实执行器模式 + 多种延时策略 + 非理想条件实验集

### 完成标准

- 能系统比较同一算法在不同真实性等级下的表现退化
- 关键真实性参数都能单独开关和调参
- obs_filter 模式可验证（debug 模式结果 = 无 filter 的结果）

### 阶段闸门

进入阶段 4 之前，必须同时满足：

- [x] 感知真实性轮 A 已完成
- [x] 控制器输入模式分离已完成，默认研究实验不得直接读取 target 真值
- [x] 至少具备丢检、亮度变化、距离相关目标大小三类近真实因素
- [x] 对同一算法能稳定生成”理想模式 vs 研究模式”的对比结果

### 阶段风险

- 如果真实性因素加得过多但不分层，平台会变得难以调试
- **轮 A 的丢检概率和亮度变化参数需要参考真实场景标定，否则可能脱离实际**

## 阶段 4：算法基线建设 `🔴 未开始`

> 实施前详细计划文档：`docs/阶段4-算法基线建设/阶段4详细开发计划.md`

### 目标

建立一套能公平比较的基线算法池，为后续筛选方向提供依据。

> **前置条件**：阶段 3 轮 A 必须完成。在理想图像（黑底+高斯亮点）上做算法比较没有意义——所有方法都会表现很好，无法区分。只有加入丢检、亮度变化等真实因素后，算法差异才会显现。

### 任务

1. **建立捕获算法基线**：
   - 大视场搜索策略（广角 → 窄角切换）
   - 光栅扫描策略（覆盖视场的扫描路径）
   - 捕获后的粗定位逻辑
   - 注意：捕获概念当前代码中完全不存在，需要新增 ATP 状态机

2. **建立跟踪算法基线**：
   - 纯比例控制（当前 BaselineTrackerProgram 的泛化）
   - PI 控制（加入积分项消除稳态误差）
   - 角度模式控制（利用云台的 ANGLE_MODE，由控制器做串级）
   - 速率模式控制（当前默认模式）
   - 每种算法作为独立 ControlProgram 实现

3. **建立预测算法基线**：
   - 无预测（当前基线，纯反应式）
   - alpha-beta 滤波器
   - 线性卡尔曼滤波器（状态=[位置, 速度]）
   - 扩展卡尔曼滤波器（状态=[位置, 速度, 加速度]，非线性运动模型）
   - 预测器的输出作为控制器的输入，形成 predictor+controller 组合

4. **建立 ATP 模式切换逻辑**（需要新增 Raspi 层状态机）：
   - 捕获 → 粗跟踪（目标首次进入视场）
   - 粗跟踪 → 精跟踪（误差持续 < 阈值）
   - 精跟踪 → 失锁（连续 N 帧丢失目标）
   - 失锁 → 重捕获（进入搜索模式）
   - 当前代码无此状态机，需要从零构建

5. **建立统一 benchmark 流程**：
   - 固定场景集（不同运动类型 × 不同延时 × 不同噪声等级）
   - 固定随机种子（可复现）
   - 固定初始条件（起始位置、初始速度）
   - 固定输出指标（跟踪率、RMS 误差、峰值误差、捕获时间、失锁次数）
   - 自动化脚本：一键跑全部算法 × 全部场景

6. **形成方法排序规则**：
   - 按场景分组排序（不能只看一个场景的排名）
   - 关注鲁棒性（最差场景的表现比最好场景的表现更重要）

### 阶段产出

- 一组可直接运行的基线算法
- benchmark 流程
- 候选方法对比表
- 第一版优先路线结论

### 完成标准

- 不同算法能在同一标准下被公平比较
- 可以明确回答下一步优先深挖哪几类方法

### 阶段闸门

进入阶段 5 之前，必须同时满足：

- [ ] benchmark 已固定输入矩阵与输出格式
- [ ] 至少有 3 类基线算法可在同一流程下批量比较
- [ ] 算法结果排序可复现，重复运行不会出现大幅漂移
- [ ] ATP 状态机已能覆盖捕获、跟踪、失锁、重捕获的最小闭环流程

### 阶段风险

- 如果 benchmark 不统一，算法结果没有比较价值
- **ATP 状态机（捕获→跟踪→瞄准→失锁）是全新模块，工作量大且需要与 Raspi 延时管线深度集成**
- 如果预测算法的输入依赖了 obs 中的真值（而非仅用 frame），对比结果将不可信

## 8. 推荐推进方式

建议采用下面的推进方式：

1. **先做阶段 0 和阶段 1**
   - 这是地基
   - 没做完不要进入算法比较
2. **再做阶段 2**
   - 没完成双轴升级，不要把当前结果称为 ATP 平台结果
   - 坐标系定义必须先于代码改动
3. **再做阶段 3 轮 A**
   - 没完成感知真实性，不要高估算法效果
   - **obs_filter 模式分离是本阶段最重要的产出**
4. **再做阶段 4**
   - 没有统一 benchmark，不要下结论说某算法更优
   - 在理想场景下算法比较无意义
5. **阶段 3 轮 B 和阶段 5 可并行**
   - 执行器真实性和平台固化可以交替推进

## 8.1 本轮边界与后续衔接

本开发文档默认**先完成 ATP 平台本体**，不在本轮直接展开通信链路联合仿真。这样处理不是忽略通信，而是为了避免在一轴、理想图像、无模式隔离的平台上过早叠加链路模型，导致结论失真。

通信链路应在满足下面条件后，再单独立项进入下一轮开发：

1. 双轴 ATP 底座已完成
2. 研究模式与近真实模式已完成
3. benchmark 已能稳定比较 ATP 算法
4. 失锁、重捕获和模式切换机制已经具备

下一轮单独文档应至少覆盖：

- 光链路参数定义
- 指向误差到链路损失的映射
- ATP 与通信联合指标
- 基于链路状态的策略切换逻辑
