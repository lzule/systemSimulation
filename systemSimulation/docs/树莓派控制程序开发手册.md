# 树莓派控制程序开发手册

> 这份手册专门回答三个问题：
> 1. 你自己写的树莓派控制程序到底是什么
> 2. 它在当前仿真里的接入点在哪里
> 3. 写完以后该怎么跑、怎么测、怎么看结果

## 1. 先理解你要写的是什么

在这个项目里，树莓派不是单独起一个外部进程，也不是去改底层运行时。

你写的内容，本质上是一个“控制程序类”：

- 系统每过一个仿真步，就会把当前观测交给它
- 你的程序根据观测做判断
- 然后返回一组控制命令
- 命令再交给云台、相机等实体去执行

最小接口只有一个：

```python
class ControlProgram:
    def on_tick(self, obs: dict) -> list[Command]:
        ...
```

对应源码可看：

- [control_program.py](../entities/raspi/control_program.py)
- [tracker_program.py](../entities/raspi/tracker_program.py)

## 2. 它在系统里的位置

整条链路可以按这个顺序理解：

1. 运行时先推进目标、云台、相机
2. 然后把这一刻的世界状态整理成一份观测
3. 树莓派实体拿到观测后，不会立刻处理，而是先经过自己的延时链路
4. 延时链路走到“处理”阶段时，才真正调用你的 `on_tick`
5. 你的程序返回命令后，命令再被送回系统，在后续时刻生效

这意味着两件事：

- 你拿到的观测不一定是“此刻最新”的
- 你发出的命令也不一定是“立刻生效”的

如果你后面做预测、状态机、重捕获，这一点一定要记住。

更完整的背景说明可以看：

- [entities/raspi/README.md](../entities/raspi/README.md)
- [runtime/README.md](../runtime/README.md)
- [simulation/bootstrap.py](../simulation/bootstrap.py)

## 3. 你能拿到什么输入

`on_tick(obs)` 里的 `obs` 不是随便传的，它至少会包含这些部分：

- `timestamp`：当前这次观测的时间
- `target`：目标状态
- `gimbal`：云台状态
- `camera`：相机状态
- `frame`：当前图像帧；有时会是空

你写程序时最常用的是：

- `obs["frame"]`：拿图像做检测
- `obs["gimbal"]`：看当前云台角度、模式、角速度
- `obs["camera"]`：看目标是否在视场内、目标像素位置等

一个很重要的现实点：

- 在某些模式下，`frame` 可能为空
- 目标不在画面里时，像素坐标可能无效
- 所以你的程序不能默认“每次都有可用目标”

## 4. 你应该把程序写成什么样

最稳妥的起步方式，不是直接套阶段 4 的复杂结构，而是先写一个最小可运行版本。

推荐模板：

```python
from __future__ import annotations

from entities.gimbal.control import RATE_MODE
from runtime.types import Command


class MyTracker:
    def on_tick(self, obs: dict) -> list[Command]:
        timestamp = float(obs.get("timestamp", 0.0))
        gimbal = obs.get("gimbal") or {}
        commands: list[Command] = []

        # 先确保云台进入你需要的模式
        if gimbal.get("mode") != RATE_MODE:
            commands.append(
                Command(
                    target="gimbal",
                    action="set_mode",
                    payload={"mode": RATE_MODE},
                    timestamp=timestamp,
                    source="my_tracker",
                )
            )

        frame = obs.get("frame")
        if frame is None:
            return commands

        # 这里换成你自己的检测和控制逻辑
        commands.append(
            Command(
                target="gimbal",
                action="set_rate_target",
                payload={"yaw_rate": 0.0, "pitch_rate": 0.0},
                timestamp=timestamp,
                source="my_tracker",
            )
        )
        return commands
```

这个模板为什么适合作为起点：

- 它先把接入链路跑通
- 它先处理“无图像帧”的情况
- 它先把命令返回结构写对
- 后面你只需要替换中间那段控制逻辑

## 5. 程序文件应该放哪里

最简单的做法，是把你的文件放在 `systemSimulation/` 工作目录下，这样最容易加载。

例如你新建：

```text
systemSimulation/my_tracker.py
```

类名叫：

```text
MyTracker
```

那运行时就用：

```text
my_tracker:MyTracker
```

如果你以后想整理成包结构，也可以写成：

```text
my_package.my_tracker:MyTracker
```

## 6. 系统是怎么加载你的程序的

项目已经帮你做好了加载入口，不需要你自己改运行时。

核心入口在这里：

- [simulation/cli.py](../simulation/cli.py)
- [simulation/headless.py](../simulation/headless.py)
- [simulation/bootstrap.py](../simulation/bootstrap.py)

加载方式是：

```powershell
conda run -n simulation python -m simulation.cli --control-program 模块名:类名
```

系统会：

1. 先创建运行时
2. 自动上电目标、云台、相机、树莓派
3. 等它们进入可用状态
4. 挂载你的控制程序
5. 按你给的模式开始跑

## 7. 先学会两种现成写法

你不用一上来就发明自己的结构。仓库里已经有两种很值得照着学的写法。

### 7.1 基础写法：直接型控制程序

代表文件：

- [tracker_program.py](../entities/raspi/tracker_program.py)

特点：

- 一个类直接实现 `on_tick`
- 自己做检测
- 自己直接返回云台命令
- 适合最小原型、简单闭环、先验证想法

如果你现在只是想写“我自己的第一版树莓派程序”，优先学这个。

### 7.2 进阶写法：总控 + 可插拔部件

代表文件：

- [atp_control_program.py](../entities/raspi/atp_control_program.py)
- [atp_state_machine.py](../entities/raspi/atp_state_machine.py)
- [trackers/rate_p_tracker.py](../entities/raspi/trackers/rate_p_tracker.py)
- [trackers/rate_pi_tracker.py](../entities/raspi/trackers/rate_pi_tracker.py)
- [predictors/alpha_beta.py](../entities/raspi/predictors/alpha_beta.py)
- [predictors/linear_kf.py](../entities/raspi/predictors/linear_kf.py)

这套结构的意思是：

- 总控程序负责主流程
- 状态机负责“搜索、捕获、跟踪、丢失、重捕获”的切换
- 跟踪器负责“当前该怎么打命令”
- 预测器负责“目标暂时看不清时怎么估计”

这套更适合：

- 你准备做多个算法对比
- 你想把“搜索”和“跟踪”拆开
- 你后面会做基线测试和批量实验

如果你只是先写一个自己的控制逻辑，不一定要直接上这套。

## 8. 观测模式怎么选

当前入口支持三种模式：

- `debug`
- `research`
- `realistic`

它们的差别，简单理解就是“你能看到多少理想信息”不同。

建议你这样用：

- 刚写第一版时，用 `debug` 或 `research`
- 想看更接近真实的表现时，再用 `realistic`
- 如果你的控制逻辑依赖更理想的输入，不要直接跳到 `realistic`

相关说明可看：

- [阶段1观测模式与输入边界.md](阶段1-问题定义冻结/阶段1观测模式与输入边界.md)

## 9. 你的第一轮运行步骤

建议严格按这个顺序走。

### 第一步：先确认程序能被加载

在 `systemSimulation/` 目录执行：

```powershell
conda run -n simulation python -m simulation.cli --help
```

然后用你自己的类名启动：

```powershell
conda run -n simulation python -m simulation.cli --no-gui --mode offline --duration 5 --obs-mode debug --control-program my_tracker:MyTracker
```

如果这一步能跑，说明三件事基本已经成立：

- 模块路径写对了
- 类名写对了
- 你的类可以被实例化

### 第二步：做一次短时无界面运行

```powershell
conda run -n simulation python -m simulation.cli --no-gui --mode offline --duration 10 --obs-mode research --control-program my_tracker:MyTracker
```

这是最适合排查逻辑问题的方式，因为：

- 运行快
- 不依赖界面
- 更适合先看有没有异常退出

### 第三步：再看近真实模式

```powershell
conda run -n simulation python -m simulation.cli --no-gui --mode offline --duration 10 --obs-mode realistic --control-program my_tracker:MyTracker
```

如果你在前两步没问题，但这里出问题，通常不是“系统坏了”，而是你的程序对输入条件假设太乐观。

## 10. 如何理解“树莓派实例中的自定义控制部分”

你可以把树莓派这一侧拆成三层看：

### 第一层：树莓派实体

它负责：

- 上电和就绪状态
- 延时链路
- 调用控制程序
- 记录一些过程状态

看这里：

- [entity.py](../entities/raspi/entity.py)
- [client.py](../entities/raspi/client.py)

### 第二层：控制程序本体

这就是你要写的部分。

它负责：

- 看观测
- 做判断
- 返回命令

看这里：

- [control_program.py](../entities/raspi/control_program.py)
- [tracker_program.py](../entities/raspi/tracker_program.py)

### 第三层：更复杂的自定义算法框架

如果你不想把所有逻辑都塞进一个 `on_tick`，就走阶段 4 这套拆分法。

它负责：

- 状态机切换
- 跟踪器替换
- 预测器替换
- benchmark 统一比较

看这里：

- [atp_control_program.py](../entities/raspi/atp_control_program.py)
- [tools/run_benchmark.py](../tools/run_benchmark.py)

## 11. 怎么测试你自己的程序

建议分三层来测，不要一上来只看最终画面。

### 11.1 第一层：树莓派侧单元测试

先跑树莓派相关测试：

```powershell
conda run -n simulation python -m unittest discover -s entities/raspi/tests -p "test_*.py" -v
```

重点价值：

- 确认树莓派实体、延时链路、控制程序装载机制本身没问题

### 11.2 第二层：运行时集成测试

再跑这些测试：

```powershell
conda run -n simulation python -m unittest tests.test_digital_twin_runtime -v
conda run -n simulation python -m unittest tests.test_phase4_algorithm_baselines -v
```

重点价值：

- 确认控制程序能在完整运行时里工作
- 确认更复杂的状态机、跟踪器、预测器链路正常

### 11.3 第三层：全量回归

最后跑全量：

```powershell
conda run -n simulation python -m unittest discover -s tests -v
```

如果你改了实体代码或者算法框架，这一步不要省。

### 11.4 第四层：无界面冒烟

文档里最值得长期保留的一条命令就是它：

```powershell
conda run -n simulation python app.py --no-gui --mode offline --duration 1.0
```

如果你是测自定义控制程序，就带上 `--control-program`。

### 11.5 第五层：算法对比测试

如果你已经不是在写“单个小程序”，而是在做多个版本对比，就用 benchmark：

```powershell
conda run -n simulation python tools/run_benchmark.py
```

这条更适合阶段 4 那种“多个算法横向比较”的场景。

## 12. 最常见的坑

### 12.1 程序加载失败

优先检查：

- 文件是不是放在 `systemSimulation/` 可导入范围内
- `--control-program` 写的是不是 `模块名:类名`
- 类是不是无参可实例化

### 12.2 一直没有控制效果

优先检查：

- `on_tick` 是否真的返回了命令
- 命令目标和动作名是否写对
- 是否先把云台切到了你需要的模式

### 12.3 程序一跑就报空值问题

优先检查：

- `frame` 是否为空
- 目标是否真的在画面里
- 你是否默认了每一帧都有有效检测

### 12.4 在 `debug` 能跑，在 `realistic` 不能跑

优先检查：

- 你的逻辑是不是太依赖理想输入
- 你是不是没有处理丢目标
- 你是不是没有处理延时和测量误差

### 12.5 搜索和重捕获逻辑越写越乱

这时不要继续把所有逻辑堆在一个 `on_tick` 里，直接参考阶段 4 的拆分方式。

## 13. 给你的实际建议

如果你现在准备开始写自己的树莓派程序，最稳的路线是：

1. 先仿照 [tracker_program.py](../entities/raspi/tracker_program.py) 写最小版
2. 先只做“能加载、能运行、能返回命令”
3. 再补“目标丢失时怎么办”
4. 再补“搜索、重捕获、预测”
5. 如果逻辑变复杂，再升级到 [atp_control_program.py](../entities/raspi/atp_control_program.py) 这种拆分结构

不要一开始就把“检测、状态机、预测、调参、benchmark”全部塞进第一版。
