## 一、潜在 Bug（可能导致运行时错误或错误结果）

### BUG-01：config.py 全局单例被 `apply_target_overrides()` 直接修改

**位置**：`simulation/headless.py:12-20`

```python
def apply_target_overrides(cfg: AppConfig) -> None:
    from config import target_cfg
    if cfg.target_type:
        target_cfg.motion_type = cfg.target_type  # ← 直接修改模块级全局单例
    if cfg.waypoints:
        target_cfg.motion_type = "waypoint"
        target_cfg.waypoints = _parse_waypoints(cfg.waypoints)
```

**问题**：`target_cfg` 是模块级单例，`apply_target_overrides()` 直接对其赋值。在同进程内多次创建 `AppConfig`（例如 GUI reset、或连续跑多次 headless）时，前一次的配置会泄漏到后一次。同时 GUI 和 headless 共用此函数（`simulation/gui/window.py:92`），reset 不会恢复全局配置。

**影响**：
- GUI 点"重置"后目标运动类型不会恢复
- 同进程多次调用 `run_headless_session` 会累积配置污染
- benchmark 工具批量运行场景时参数可能串场

**建议修复**：`TargetEntity.__init__()` 时深拷贝配置，或 `apply_target_overrides` 返回新配置对象而非原地修改全局。

**位置**：`entities/raspi/tracker_program.py:129`

### BUG-03：`GimbalEntity.get_state()` 首次调用触发 `update(0.0, timestamp)` 有副作用

**位置**：`entities/gimbal/entity.py:155-160`

```python
def get_state(self, timestamp: float) -> Dict[str, float | str | bool | None]:
    if self._last_state is None:
        self.update(0.0, timestamp)  # ← dt=0 但会推进 boot_remaining_s
```

**问题**：`DigitalTwinRuntime.__init__()` 构造时调用 `self.gimbal.get_state(0.0)` 初始化 `_last_snapshot`（runtime/digital_twin_runtime.py:47），这触发 `update(0.0, 0.0)`。虽然 dt=0 不会导致 boot 倒计时归零（`0 - 0 <= 0` 不成立），但控制器 `step()` 接收 dt 被 clamp 到 `max(1e-6, ...)`，导致内环积分器被喂入 1e-6 的 dt，产生微量积分偏移。

**影响**：首次 step 前积分器已有非零值，在极端精度要求场景下可能导致初始 tick 的控制输出有微小偏差。

**建议修复**：`get_state()` 首次调用时构造一个"零值" GimbalState，不调用 `update()`。

### BUG-04：`CascadedController2Axis.step()` rate_tick 未命中时用 `dt` 替代 `rate_dt` 积分

**位置**：`entities/gimbal/control.py:138-139`

```python
if not ticks.rate_tick:
    last_cmd = self._compute_inner_cmd(yaw_rate_dps, pitch_rate_dps, dt)  # ← 用的是仿真 dt 而非 rate_dt
```

**问题**：当 rate_dt > dt 时（正常情况下 rate_loop_hz=200，dt=0.005，rate_dt=0.005），rate_tick 应该每步都命中。但如果 `rate_loop_hz` 配置得比仿真步频低（例如 100Hz vs 200Hz 仿真），则会出现 rate_tick 未命中的 tick，此时 `_compute_inner_cmd` 用 `dt`（0.005）而非 `rate_dt`（0.01）做积分，积分步长不一致。

**影响**：在 rate_loop_hz < 仿真频率时，积分器行为与预期不符，可能导致 PID 输出偏差。

**建议修复**：非 rate_tick 时应该跳过积分更新（只保持上次输出），或用 rate_dt 积分但只在 rate_tick 时执行。

### BUG-05：`RaspiEntity.set_delay_profile()` 重建 `RaspiDelayModel` 丢弃 fifo 队列中积压的观测

**位置**：`entities/raspi/entity.py:74-94`

```python
def set_delay_profile(self, profile: Dict[str, float]) -> CommandResult:
    ...

```

**问题**：`set_delay_profile()` 直接用新 `RaspiDelayModel` 覆盖旧实例。如果旧模型正在处理中（READING/PROCESSING/SENDING）或 fifo 队列中有积压观测，这些状态会静默丢失。当前 GUI 的延时微调功能会触发此路径。

**影响**：GUI 运行中调节延时会导致正在处理的观测被丢弃，可能导致一拍控制输出为空。

**建议修复**：保留旧模型状态（至少让已进入管线的工作完成），或至少在丢弃前记录日志。

### BUG-06：`headless.py` realtime 模式未驱动 Raspi 控制

**位置**：`simulation/headless.py:67-78`

```python
# realtime 模式
t_end = time.time() + cfg.duration_s
while time.time() < t_end:
    snapshot = runtime.step(1)
    ...
    time.sleep(runtime.dt_s)  # ← sleep 阻塞，但 runtime.step 内部已经是单线程 tick
```

**问题**：`runtime.step()` 内部已经执行了 Raspi 的 update 和控制程序调用，所以 realtime 模式本身没有逻辑错误。但 `time.sleep(runtime.dt_s)` 用的是 wall-clock sleep，精度不够时会导致实际仿真步频低于 dt_s 指定的频率（因为 step 本身也消耗时间）。

**影响**：realtime 模式的时间推进不精确，可能导致仿真时长与真实时长不一致。

**建议修复**：使用 `time.perf_counter()` 计算已用时间后 sleep 补偿差值，与 `DigitalTwinRuntime._loop()` 和 `SimWorker.run()` 中的做法一致。

### DESIGN-06：`apply_delay_profile()` 延时预算分配方式 `25%+50%+25%=100%` 实际超标

**位置**：`simulation/bootstrap.py:15-32`

```python
def apply_delay_profile(runtime, delay_ms):
    total_s = delay_ms / 1000.0
    runtime.raspi_client.set_delay_profile(
        image_read_delay_s=total_s * 0.25,    # 25%
        image_process_delay_s=total_s * 0.50,  # 50%
        state_read_delay_s=total_s * 0.25,    # 25%
        command_tx_delay_s=total_s * 0.25,    # 25%
    )
```

**问题**：注释说"比例≈25%|50%|25%"，但 `obs_delay = max(image_read, state_read) + jitter`（raspi/entity.py:128），所以实际端到端延迟是 `max(25%, 25%) + 50% + 25% = 100%`。看起来注释是对的。但 `command_tx_delay_s` 多传了 0.25，如果未来有人改成顺序执行（非并行），总延迟就变成 125%。

**建议**：注释中明确说明 image_read 和 state_read 是并行执行的，或改为 `state_read_delay_s=0` 让二者完全相等。

### DESIGN-08：`GimbalPlant2Axis.step()` 中 yaw 无角度限制

**位置**：`entities/gimbal/model.py:67`

```python
self.yaw_deg_internal += self.yaw_rate_dps * dt  # ← yaw 可无限旋转
```

**问题**：pitch 有 `pitch_min_deg` / `pitch_max_deg` 的机械限位保护，但 yaw 没有。虽然物理上云台 yaw 可以连续旋转（无机械限位），但 `config.py` 中定义了 `angle_min_deg=-90` 和 `angle_max_deg=90`，这些参数在 yaw 轴上完全被忽略。

**影响**：如果控制器发出大 yaw_rate 命令，yaw 会超出 `angle_min_deg` / `angle_max_deg` 范围。在角度环模式下，`_compute_outer_rate_ref` 会产生很大的误差信号驱动 yaw 回来，但中间的 transient 可能不符合物理约束。

**建议**：明确 yaw 轴是否应该限制。如果不限制，在文档中说明 `angle_min_deg`/`angle_max_deg` 只对 pitch 有效；如果限制，在 model.py 中加上类似 pitch 的限位逻辑。

### STYLE-04：`BaselineTrackerProgram` 中 `_build_mode_command_if_needed` 每次调用都检查模式

**位置**：`entities/raspi/tracker_program.py:76-81`

```python
def _build_mode_command_if_needed(self, obs, timestamp):
    gimbal_mode = obs.get("gimbal", {}).get("mode", "")
    if gimbal_mode == "ANGLE_MODE":
        return [Command(target="gimbal", action="set_mode", payload={"mode": "RATE_MODE"}, ...)]
    return []
```

**问题**：每个 tick 都发送 `set_mode(RATE_MODE)` 命令（当云台在 ANGLE_MODE 时）。这意味着在 boot 完成后、第一次控制 tick 时，会发送一个 mode 命令；之后云台已经在 RATE_MODE，这个检查就不再产生命令。这本身没问题，但云台初始模式是 ANGLE_MODE（control.py:42），如果不发 mode 切换命令，tracker 的 rate 命令不会生效。

**潜在问题**：如果 tracker_program 被延迟加载（经过 delay pipeline 后才执行），第一个控制 tick 之前的仿真 tick 里云台在 ANGLE_MODE 接收 rate 命令，rate 命令会被 `_latest_rate_cmd` 覆盖但不生效（因为 mode 是 ANGLE_MODE 时外环输出覆盖 rate ref）。

## 六、性能与资源问题

### PERF-01：`render_beacon_frame()` 每次渲染都创建全分辨率 Gaussian blob

**位置**：`entities/camera/model.py:70-75`

```python
xs = np.arange(w, dtype=np.float32)
ys = np.arange(h, dtype=np.float32)
gx = np.exp(-0.5 * ((xs - u) / sigma) ** 2)
gy = np.exp(-0.5 * ((ys - v) / sigma) ** 2)
blob = np.outer(gy, gx)
```

**问题**：每次渲染都分配 640×480 的 float32 数组（~1.2MB），做 outer product。在 200Hz 仿真中每秒分配 240MB。虽然 Python GC 能处理，但对长时间仿真（如 60s）可能产生 GC 压力。

**建议**：使用局部 ROI 渲染（只渲染目标周围 3σ 范围的像素），或预分配缓冲区。

---

### PERF-02：`_copy_frame()` 在 debug 模式下每 tick 都做 image.copy()

**位置**：`entities/camera/entity.py:222-230` 和 `simulation/obs_filter.py:71`

**问题**：`CameraEntity.get_frame()` 和 `ObsFilter.filter_obs()` 都做了 `image.copy()`。在 640×480 uint8 下这是 300KB 的拷贝，200Hz 下每秒 60MB。两层 copy 意味着每 tick 两次完整图像拷贝。

**建议**：评估是否可以只在真正需要隔离时 copy（例如 copy-on-write）。
